# Decisions

Dated log of design and technical decisions. Newest first. Each entry gives the decision, its reason and where it is specified.

## 2026-10-15
- **Select and Select Box select shapes, joints and (by click only) the root; a click on a shape selects the shape, never its body.** Bodies are selected from the Hierarchy (#19). Reason: confirms the existing §5.4 hit rule; bodies have no hit area of their own, and the tools then need no body resolution or `js/model/queries.js`. Confirmed by the owner on 2026-10-15: Manipulate (#17) moves the body of a selected shape. (DESIGN §5.4, §5.5; docs/architecture.md, Tools)
- **Click semantics:** the target is the topmost hit; ALT picks the hit just below the topmost selected hit, wrapping, so repeated ALT + clicks cycle through overlapping objects. No modifier selects only the target, SHIFT toggles it, CTRL removes it (CTRL wins); an empty click clears the selection without modifiers and does nothing with them. Reason: SHIFT toggle was already specified; CTRL is free in the selection tools and gives a remove that a toggle cannot express for boxes; ALT was unused and a joint anchor (8 px) otherwise always hides the shapes under it. Plain clicks never cycle, so clicking a selected object keeps it. (DESIGN §5.5; docs/architecture.md, Tools)
- **Selection boxes take shapes entirely inside them and joints whose anchor is inside, never the root; none replaces, SHIFT adds, CTRL removes (CTRL wins), modifiers read at the release.** Containment is tested with `shapeBounds` against the world box, which is exact for an axis-aligned box. Reason: containment avoids grabbing large background shapes when boxing limbs of a dense ragdoll and needs no new intersection geometry; the root contains everything and would turn every box into "select the ragdoll", which Manipulate and Group would then have to untangle. Intersect mode is deferred. Containment confirmed by the owner on 2026-10-15. (DESIGN §5.5; docs/architecture.md, Tools)
- **A drag in Select also draws a selection box (any modifiers), not only SHIFT + drag; Select Box differs only in that a click acts as an empty box.** Reason: the spec left a plain drag in Select undefined, and a dead drag is surprising; Select never moves objects (Manipulate does), so there is no conflict. Confirmed by the owner on 2026-10-15. (DESIGN §5.5)
- **The selection changes only at the release, with no live preview of the boxed objects; aborting needs no restore.** Reason: live updates would emit a `selection` event per move to every panel and need a restore of the exact previous lists and focus on abort, which `Selection` has no API for; the box outline is enough feedback for #13. Live preview can be added later in the overlay. (DESIGN §5.5; docs/architecture.md, Tools)
- **Box selection goes through `ToolView.boxTest` / `ToolContext.boxTest`, backed by a new `boxTest(model, box, { pose })` in `js/viewport/hit.js`; the shape validity rule moves to an exported `shapeGeometryValid` in `lib/geometry.js`, used by `pointInShape`.** The two tools share `marqueeTool` in `js/tools/select-box.js`. Reason: like `hitTest`, the box test must use the displayed pose, which only the viewport knows; one validity rule keeps clicks and boxes skipping the same shapes; a shared lifecycle mirrors `dragShapeTool` for Circle and Box. (docs/architecture.md, Tools)
- **Select is active on load and is the toolbar's pressed button and roving stop; New and Load keep the active tool.** No code beyond registering the tool: the registry already starts with Select and `js/main.js` already refreshes the toolbar from `tools.active`. (DESIGN §5.5; docs/architecture.md, Tools)
- **Tools overlay geometry is fixed so its sizes add up:** 4 px from the outer edge to the buttons (1 px border plus 3 px padding), 2 px gaps between all items, separators 5 px tall; one column 40 × 299 px, two columns 76 × 149 px (selection + manipulation, creation + joints, 4 px apart, the middle separator hidden). The two-column threshold is derived, not a constant: the strip plus its two 8 px margins (315 px). Reason: "1 px border, 4 px padding" gave a 42 px strip, not the 40 × 299 the spec stated, and the two-column size had no arrangement behind it; deriving the threshold keeps it right if a metric changes. Viewport minimum height becomes 168 px. (DESIGN §5.2, §5.5; docs/architecture.md, Module map)
- **The overlay's testable rules live as DOM-free exports of `js/viewport/toolbar.js`** (`TOOL_BUTTONS`, `TOOLBAR_MARGIN`, `toolbarSize`, `toolbarColumns`), allowed in `tests/` by the existing UI exception, and the framing insets as `framingInsets` in the core `js/viewport/bounds.js`. `toolbar.width()` returns `toolbarSize(columns).width` instead of measuring. Reason: no new module for four small functions, and the column rule belongs next to the DOM that applies it; framing insets are a framing rule, already core. A computed width never forces layout during framing; the CSS must match it, which is checked in the browser. (DESIGN §5.4, §5.5; docs/architecture.md, Dependency rules, Module map, Viewport camera, grid and snapping)
- **`TOOL_BUTTONS` entries carry `shortcut` (the `TOOL_SPECS` hotkey) instead of `hotkey`,** so each entry is a `HeaderAction` and `actionTitle` builds the tooltip unchanged; buttons also get `aria-keyshortcuts`. Reason: one tooltip text builder for header and tools, as §5.5 requires ("built like the header tooltips"). (DESIGN §5.5; docs/architecture.md, Module map)
- **Unbuilt tools are disabled with "(not available yet)", read from the `tool:<id>` actions; at most one button is pressed, and none before Select (#13) is registered.** Confirms the #12 rule from the toolbar side: `js/main.js` refreshes every button from `actions.isEnabled`/`reason` on `tool` and `mode` events, so tools light up as their issues register them, with no toolbar change. Reason: "exactly one pressed, Select active on load" contradicted the registry rule that no tool is active without Select. (DESIGN §5.5; docs/architecture.md, Editor boot)
- **Toolbar keyboard and pointer details:** Up/Down and Left/Right both move linearly in either layout; Enter/Space use the native button click and keep focus; a pointer click on an enabled button moves focus to the viewport host, on a disabled one it does nothing; Esc only hides the tooltip and is consumed; the roving stop returns to the active tool when focus leaves; a wheel over the overlay is swallowed. Reason: handling Space in `keydown` risks a second activation from the native keyup click in some browsers; a two-dimensional grid for at most eight buttons is not worth a second navigation model; a wheel over the overlay would otherwise scroll the workspace. (DESIGN §5.5, §5.9; docs/architecture.md, Module map)
- **The tooltip is one shared, `aria-hidden`, fixed-position element on `body`, created on first show, placed 8 px right of its button; `attachTooltip` returns `{ update, detach }`.** Reason: inside the isolated Viewport panel it would be clipped and could not rise above neighbouring panels; creating it lazily keeps `js/tooltip.js`, and so `js/viewport/toolbar.js`, loadable in Node; `update` lets a visible tooltip follow a mode change. (DESIGN §5.5; docs/architecture.md, Module map)
- **No layout version change for #87.** Stored layouts that still name a `tools` panel are already rejected by `validateLayout` (version 1, or an unknown panel id) and replaced by the default with a warning, which is never an error; the raised Viewport minimum applies when rects are computed, not to stored sizes. Drag & drop loading listens on `#panel-viewport` (#28), and the overlay never stops drag events. Reason: the 2026-10-14 decision already moved the record to version 2 without migration when Tools left the dock; only tests were missing. (DESIGN §5.2, §5.3, §5.5; docs/architecture.md, Dock layout, Module map)
- **Circle and Box: a click without a drag creates the shape at its schema default size (circle radius 0.25 m, box 0.5 × 0.5 m) centered at the snapped click point, whatever modifiers are held; with grid snap on, the dragged circle radius is rounded to the minor spacing (`snapLength`), never below it.** A press becomes a drag once the pointer has moved 4 px from the press point and stays one until release; a drag that ends with a size of 0 is refused. Reason: owner decisions for #14; a click must give a usable shape instead of a refused zero-size one, and latching the drag keeps a drag that comes back near the press from turning into a default shape. The radius is snapped as a length, not as a snapped pointer, so it lands on multiples of the step. (DESIGN §5.4, §5.5; docs/architecture.md, Tools)
- **Box ALT enforces symmetry in both axes, the same effect as CTRL: the box is centered on the anchor; ALT and CTRL together are the same as either; SHIFT still makes the final box square.** Sizes and centers follow one per-axis rule with an example in §5.5. Reason: owner decision for #14; DESIGN gave ALT "symmetry" and CTRL "anchor at the center", and the owner confirmed they are the same operation. This replaces the earlier interpretation that centered only the drag's shorter axis under ALT. (DESIGN §5.5; docs/architecture.md, Tools)
- **`createShapeBody({ position, angle, shape }, label?)` in a new `js/commands/create.js` is the one command for shape creation;** it appends the body with its fixture in a single `add` op, sets `rootBody` when it is `null`, names objects after their id numbers (`body_<n>`, `<type>_<n>`), validates its arguments before allocating ids, and returns the shape uid. Tools convert world drafts to root-local data (`toLocal` of the snapped center, body angle = −root angle). Reason: one undo step and one `change` per creation, exact undo and redo through the existing `add`/`set` inverses, and the same command serves Polygon (#15); keeping frames out of the command keeps it free of camera and snapping. (DESIGN §2.1, §2.2; docs/architecture.md, Commands and undo, Module map; docs/schema.md)
- **Circle and Box share a core factory, `dragShapeTool` in `js/tools/drag-shape.js`, with their draft geometry exported as pure functions (`circleDraft`, `boxDraft`).** The preview uses only `circle`, `rect`, `fill` and `stroke` of the handed `PIXI.Graphics`, in `COLORS.highlight`. Reason: the two tools differ only in their geometry; Polygon (#15) has a multi-click lifecycle and does not use the factory. Pure draft functions make the modifier table testable without events, and a fixed Graphics surface lets tests record drawing with a fake. (docs/architecture.md, Tools, Module map)
- **A middle press during a left tool drag stays specified as a pan, with a provisional known limitation:** if the browser takes pointer capture away on that press, the existing lost-capture rule cancels the drag and the document is left as it was. No code change in #12. Reason: the release was only observed with events injected through the Chrome DevTools Protocol, whose `buttons` mask may have dropped the left button, so it may not happen with a physical mouse; the fallback is safe (one aborted drag, no data change), zoom during a drag works, and Space + drag remains a pan path. If a real browser reproduces it, a fix (such as re-capturing while the primary button is still down) is specified then. (DESIGN §5.4, §12; docs/architecture.md, Tools)
- **The tool cursor reaches the host through the `--tool-cursor` CSS custom property,** set by `js/viewport.js` in `ToolView.setCursor` and read by `#viewport-host { cursor: var(--tool-cursor, default) }`; navigation keeps writing the inline `cursor` (`grab`/`grabbing`, else `''`), which overrides the stylesheet. Reason: DESIGN §5.5 wants the tool cursor except while navigating; using CSS precedence keeps `attachInput` unaware of tools' cursors and the registry unaware of navigation, with no shared state or signature change. (DESIGN §5.5; docs/architecture.md, Tools, Module map)
- **`createEditor` gets no `tools` option; the mode reason of a registered `tool:<id>` action is checked in the browser until #14,** whose first tool (`circleTool`) adds the Node test to `tests/editor.test.js` (refused with "not available in *Mode* mode" where `tool.circle` is not allowed). Reason: an injection option would be public API added only for one test, while the registry itself is already tested directly and the reason function is the same `modeReason` the `undo` tests cover; the gap closes with the next tool issue. (docs/architecture.md, Editor composition, Module map)
- **Name labels:** an empty name shows the object's id; the root and joint labels sit above and to the right of their gizmo, and a body label is centered just below the body origin. Reason: a centered body label covered the center-of-mass mark whenever the center sits at the origin, and a nameless object would otherwise have no label at all. (DESIGN §5.4; docs/architecture.md, Module map)
- **The Contacts overlay is a stored setting with a working checkbox that draws nothing until Simulate mode exists (#54).** Reason: DESIGN already limits contacts to Simulate mode, which is not built; disabling the checkbox would need a reason text and would be removed again by #54. (DESIGN §5.3, §5.4; docs/architecture.md, Module map)
- **#12 UI accepted as built:** buttons pressed or released while another is held are read from `pointermove` with `button ≥ 0`; hover is throttled with `requestAnimationFrame` (not the PIXI ticker) and also cleared on window blur; `Viewport` exposes `gizmos` and `hitTest(screen)`; the gizmo layer draws nothing while the camera has no size, and a model `reset` clears hover. Reason: each follows the Pointer Events model for chorded buttons or has no visible effect beyond the spec. (DESIGN §5.4, §5.5; docs/architecture.md, Tools, Module map)
- **A tool handler that throws during a press always aborts it, `pointerUp` included:** the registry closes the press, runs `cancel()` (tool cancel, then `history.cancelGesture()`) and rethrows; nothing is recorded. This replaces "`endGesture()` also when `pointerUp` throws", which contradicted the general rule. Reason: one rule for every handler; a throw is a bug, and reverting the whole operation keeps "one operation, at most one undo step" and leaves no half-built result or stale tool state (`endGesture` would record a partial step without ever calling `tool.cancel()`). (DESIGN §1, §5.5; docs/architecture.md, Tools)
- **A cancelled press also ends at the first move without the primary button or at the next left press,** not only at its release. Right presses stay ignored until then. Reason: after a cancel caused by lost capture or blur the release may never reach the host, and the press must not block the next one. (DESIGN §5.5; docs/architecture.md, Tools)
- **A joint `anchor` that is missing or not a finite pair is not placed:** it is not framed, not hit and draws nothing; missing body and root positions stay (0, 0), as in the scene. `js/viewport/bounds.js` changes to match `js/viewport/placement.js` (it framed a missing anchor at the root origin). Reason: two rules for the same data disagreed; a gizmo at the root origin for a malformed joint would be misleading and could steal clicks from the root, while a body still needs a frame for its shapes to be drawn and reported. (DESIGN §5.4; docs/architecture.md, Module map)
- **#12 core details accepted as built:** `js/viewport/hit.js` imports `ROOT_UID` from `js/model/model.js` (core to core, like `placement.js`); `defineTool` ignores `label`, `hotkey`, `capability` and unknown members in a definition and throws `TypeError` for a handler, `cursor` or `hover` of the wrong type; `key()` also refuses the legacy `Esc` key value; with no active tool the cursor is `'default'`; `jointZeroAngle` treats an anchor within 1e-9 m of bodyB's origin as coinciding; `pointInShape` uses the even-odd rule, so concave and self-intersecting drafts are hit as drawn; `shapeMass` uses the absolute polygon area (a clockwise polygon weighs as its counter-clockwise twin; a concave draft counts its own area, where Box2D would hull it) and gives mass 0 for a negative or non-finite density. Reason: each keeps drafts and invalid files usable in the viewport, matches Box2D for every valid shape, or has no visible effect; type errors in a tool definition surface at load instead of at the first event. (DESIGN §5.4, §5.5; docs/architecture.md, Tools, Module map)
- **`createEditor` builds the tool registry on the #12 branch before it merges,** and its own `history.cancelGesture()` `mode` listener is removed in the same change; the transitional state, with both the registry module and the old listener, is accepted only on the branch. Reason: until then `escape`, `tool:<id>` actions and mode-change cancellation ignore tools, and two cancellation listeners must never coexist. (docs/architecture.md, Editor composition, Module map)
- **#12 gizmo and tool overlay views are stacked by `js/viewport.js` on the stage above `scene.view` (grid, scene, gizmos, tool overlay), and #12 removes the scene's empty world `gizmos` and screen-space `overlay` containers; the scene keeps no joint entries.** Both redraw from a `PIXI.Ticker.shared` callback like the grid and the scene, with no ticker parameter, and whoever calls `scene.setPose` also calls `gizmos.invalidate()`. Reason: #11 built those containers as empty placeholders from the earlier plan, while the #12 spec draws every gizmo, highlight and overlay in screen space from `js/viewport/gizmos.js`; stacking views on the stage matches how the grid is already added, keeps `Scene` unchanged, and leaves one owner per layer. The scene emits no pose event, so invalidation stays with the pose's owner. (DESIGN §5.4; docs/architecture.md, View sync, Module map)
- **`openSettings` returns `{ close, refresh }`, and `js/main.js` calls `refresh()` on `history`, `mode` and model `reset` events.** The popover keeps reading document data only through its adapter and subscribes to nothing but `settings`. Reason: pixels per meter changes through undo, redo and resets, and its editability through mode changes and gestures, none of which the adapter can signal; a refresh call keeps the popover free of model, history and modes imports, and a focused field is not overwritten unless it became read-only. (DESIGN §5.3; docs/architecture.md, Editor boot, Module map)
- **The grid and scene redraw from `PIXI.Ticker.shared`, and `createViewport` creates its application with `sharedTicker: true`,** instead of passing a ticker to `createGrid` and `createScene`. Reason: with the shared ticker the application's render (low priority) runs after the redraw callbacks (normal priority) in the same frame, so a change never shows one frame late, and the module signatures stay as specified. The cost is an implicit contract: those modules only work inside an application created this way. Ordering and teardown to be verified in the browser. (DESIGN §12; docs/architecture.md, View sync, Viewport camera, grid and snapping)
- **`createEditor` throws `TypeError` when `settings` is given and is not a `Settings` instance.** Reason: a plain object or a `restore` result passed by mistake would otherwise fail later at the first `get`, far from the cause. (docs/architecture.md, Editor composition)
- **A left press while Space is held counts as a drag, even without movement, so its release does not toggle Play/Pause.** Reason: the press starts a pan; toggling playback after a click the user meant as a pan would be a surprise, and "without a drag" is read as "without a pan gesture". (DESIGN §5.9)
- **`+`, `=` and `-` repeat while held.** Reason: they are viewport navigation keys handled by the viewport, not §5.9 hotkeys, and continuous zoom on a held key is what navigation keys do elsewhere; the §5.9 repeat rule is about actions that must not fire twice. (DESIGN §5.4)
- **Closing the Settings popover with its button or an outside press commits a pending valid number and reverts an invalid one; Esc reverts the field being edited, then closes.** Reason: closing moves focus away, which is a blur, so it follows the blur rule; Esc means cancel everywhere else. (DESIGN §5.3)
- **The viewport key summary is a visually hidden `<p id="viewport-keys">` inserted right after the viewport host,** not inside it. Reason: `aria-describedby` works with any element in the document, and keeping the host's only content the canvas avoids text inside the `role="application"` region. (DESIGN §5.4; docs/architecture.md, Module map)
- **Framing insets are 16 px on every side until the Tools overlay exists; its issue (#87) adds the overlay width on the left.** Reason: DESIGN §5.4 defines the left inset as overlay width plus 16 px, and the width is 0 while there is no overlay. (DESIGN §5.4; docs/architecture.md, Viewport camera, grid and snapping)
- **Sprites display mode hides the whole shapes layer for now; hover and selection outlines will be drawn in the gizmos layer (#12), and sprites appear with the asset store (#21).** Until then the viewport shows only the grid in Sprites mode. Reason: DESIGN §5.4 keeps only hover and selection outlines in that mode, and those belong with the other highlights; hiding one layer is simpler than styling every shape as invisible. (DESIGN §5.4; docs/architecture.md, View sync)
- **Grid colors:** lines white at alpha 0.07 times the fine-level ramp (fine) and 0.16 (coarse); X axis `#e0524f` and Y axis `#58b85c` at alpha 0.9 (about rgb(204, 77, 74) and rgb(82, 169, 86) over the `#1b1d21` background), drawn over the lines. Reason: DESIGN fixes only red and green axes; the values are the implementer's choice, kept faint so shapes stay readable, and live as constants in `js/viewport/grid.js`. (DESIGN §5.4; docs/architecture.md, Module map)
- **Tool ids, labels, hotkeys, capabilities and toolbar groups live in one core table, `TOOL_SPECS` in `js/tools/tool.js`.** `defineTool` copies them into each tool, `HOTKEYS` builds its `tool:<id>` rows from it (first, for all eight tools, registered or not), and the Tools overlay builds `TOOL_BUTTONS` from it, adding only icons. The registry's `toolForHotkey` is dropped: tool hotkeys are ordinary `tool:<id>` actions, registered by `createEditor` for registered tools only, so unbuilt tools report "not available yet" through the existing action rule and the toolbar reads enabled state and reason from the actions like the header does. Reason: the plan had three copies (tool objects, hotkey rows, toolbar buttons) of the same ids and keys, and a static hotkey table cannot be built from tool objects that do not exist yet. (DESIGN §5.5, §5.9; docs/architecture.md, Tools, Actions and hotkeys, Module map)
- **The tool registry owns cancellation.** It is built right after `modes` and subscribes first to `mode`; `tools.cancel()` cancels the tool and any open gesture (also one it did not open), replacing the editor's `history.cancelGesture()` listener. It also watches `history`: when its press is open but the gesture was closed elsewhere (Undo, reset), it cancels the tool, so Undo during a drag needs no special case in the `undo` action. After a cancel, the rest of that press is swallowed, so a release after Esc never completes the operation. Reason: tools hold local state that a history-only cancel would leave stale. (DESIGN §1, §5.5; docs/architecture.md, Editor composition, Tools)
- **The registry completes pointer events and binds to the view late.** Input passes screen coordinates, buttons, modifiers and click count; the registry adds `world` and root-local `local` from the camera and the root transform. `hitTest`, the cursor and overlay invalidation reach tools through `bindView`, called by the viewport, and are inert until then. Tools are factories with closure state. Reason: the registry and the tools stay core and testable under Node, with no viewport and no shared state between editors. (docs/architecture.md, Tools)
- **Without a registered Select tool, no tool is active.** The registry starts on `select` when it exists and falls back to it on mode changes; Select is registered since #13, so the editor starts with it active; the no-tool fallback only remains for registries built without it. Reason: lets the creation tools (#14–#16) land before #13 without a stub Select. (DESIGN §5.5; docs/architecture.md, Tools)
- **Creation tools change the document once, on completion, then select what they created and stay active.** They preview in the tool overlay while drawing; the create command runs inside the final release's gesture. The selection gets the new shape (or joint), never its body, matching what a viewport click selects. A new shape body sits at the shape's center with the opposite of the root's angle, with the shape stored around the body origin. Reason: a model write per drag step would create invalid intermediate shapes (radius 0) and churn every view, and creating then switching to Select would break drawing several shapes in a row; the body placement gives Manipulate a natural pivot and keeps the drawn orientation when the root is rotated. Not a format change. (DESIGN §2.2, §5.5)
- **Tool input rules:** tools get left and right presses and every move; middle and Space + left stay navigation; a left drag owns the pointer (other buttons ignored); modifier changes and pans during a drag re-send the last position; lost capture or window blur cancels; Esc never reaches `tool.keyDown`. Reason: the Box modifiers and the Polygon right click need these, and a drag that silently continues after the pointer is lost leaves a gesture open. (DESIGN §5.5, §12; docs/architecture.md, Tools)
- **Hit testing is a fixed order with screen-space radii:** joints within 8 px, then the root within 12 px, then shapes containing the point or within 4 px, later objects first; bodies and sprites are never hit, invalid geometry is skipped, and the displayed pose is used. Reason: gizmos are drawn above shapes and must win; screen-space tolerances keep small shapes and points clickable at any zoom; display-mode independence was already decided. (DESIGN §5.4; docs/architecture.md, Module map)
- **Gizmos, feedback and overlays are drawn in one screen-space layer redrawn whole when dirty, at most once per frame,** with sizes and colors in a core `js/viewport/style.js` and world placement in a core `js/viewport/placement.js`. Joint arcs and needles are measured from a zero direction (anchor → bodyB origin at rest, turned with bodyA). Selection is 2 px in `#5b9cf5`, hover 1 px, invalid red wins over both. Reason: constant-size gizmos in a scaled world container would need the unverified scaled-stroke technique; a few dozen gizmos are cheap to redraw; hit testing, gizmos and the Hinge tool need the same anchor and zero-direction math; "relative to bodyA" gave no direction to draw from. (DESIGN §5.4; docs/architecture.md, View sync, Module map)
- **Overlays are editor settings (`overlay.names`, `overlay.centers`, `overlay.contacts`, default off) in a new Settings group;** the settings record stays version 1 because missing fields restore to defaults. #12 draws names and centers of mass (Box2D's mass rule); contacts are drawn by Simulate mode (#54), and the preview environment is built with #54 and #38. Invalid feedback is an input of the gizmo layer (`setInvalid`), fed once Problems (#26) runs validation. Reason: §5.3 deferred the overlay toggles to the overlays issue; contacts and the preview environment need a live world, and invalid state needs validation, neither of which exists in #12. (DESIGN §5.3, §5.4; docs/architecture.md, Module map, View sync)
- **#11 implementation details the spec left open are accepted as built:** the stored settings record nests by key prefix (`{ version, grid, snap, display }`), and a record with a missing or other `version` is ignored as a whole with one warning, like the stored layout; the camera starts at (0, 0) and 32 px/m, which matches the default `pixelsPerMeter` and is replaced by framing on start; under a pose, a joint anchor follows its `bodyA` (the parent, DESIGN §2.4) and otherwise stays at rest; `shapeBounds` throws `TypeError` for an unknown type or an empty polygon, and framing skips shapes that throw or give non-finite bounds; grid fine lines with opacity 0 are omitted, lines at world 0 are kept and the axes are drawn over them; `js/units.js` converts single numbers and throws `RangeError` when `m` has no valid `pixelsPerMeter`. Reason: each follows an existing rule (versioned stored records, FK rotates children about anchors carried by the parent, drafts and invalid files must still display) or has no visible effect, and keeping the conversion scalar leaves `vec2` handling to the inspector, which knows the field shape. (DESIGN §5.3, §5.4; docs/architecture.md, Module map)
- **The viewport camera stores `scale` in CSS px per meter, independent of `pixelsPerMeter`,** clamped to 2–10 000 px/m, with `center` clamped to ±10 000 m. Changing `pixelsPerMeter` keeps shapes in place on screen and resizes the sprites; resizing the viewport keeps `center` and `scale`. The camera is session state, framed to everything on start, New, Load and recovery. Reason: a zoom factor relative to `pixelsPerMeter` would make the limits, the grid density and the float range depend on file data, and showing sprites change size is exactly what the setting does. (DESIGN §5.4; docs/architecture.md, Viewport camera, grid and snapping)
- **Wheel zoom is `2^(−Δy / 400)` (`2^(−Δy / 100)` for Ctrl, i.e. trackpad pinch) around the pointer, and `+`/`-` zoom by √2 around the center;** there is no keyboard pan. Reason: DESIGN gave no rate or keyboard zoom; F and Home already bring any content into view without a pointer, and arrow keys stay free for tools. Rates are provisional until checked in browsers (DESIGN §12). (DESIGN §5.4, §12)
- **Framing fits the bounds of shapes, joint anchors and the root position, grown to at least 1 m (4 m for an empty ragdoll), without sprite images,** with insets of 16 px plus the Tools overlay width on the left. Reason: sprite sizes need textures, which live outside the core and the model; shapes are what users place sprites on, and a point-sized selection (a joint) needs a finite box. (DESIGN §5.4; docs/architecture.md, Module map)
- **The grid has a configurable size and subdivisions (defaults 1 m and 10) and draws at most two adaptive levels,** the finest at least 8 px apart (fading in up to 32 px) and the next coarser one; levels above the major spacing step by 10. Reason: §5.3 listed "grid size" in Settings while §5.4 fixed 1 m / 0.1 m; fixed levels become a solid fill when zoomed out. (DESIGN §5.3, §5.4)
- **Grid snap rounds to the minor spacing in world coordinates, whatever level is displayed and whether the grid is shown;** it applies to points that tools place or drag, circle radii round to the step, and sprite edit, Pose, inspector fields and Hierarchy additions never snap. SHIFT angle snap stays fixed at 15° and applies to the edited angle in its own frame. - **Model changes are batched per transaction and the viewport flushes once per frame.** The model emits one `change` event (list of add/remove/set/move) per commit, undo, redo or cancelled gesture, and `reset` on New/Load/recover; the scene keeps PIXI display objects keyed by uid and only updates dirty entries. Reason: views always see a consistent model after compound commands, and long drags cost one redraw per frame. (docs/architecture.md, Change notifications, View sync)
- **One `Emitter` class in `lib/emitter.js`** serves the editor core and `RagInstance`: synchronous, in order, one payload, `on` returns an unsubscribe function, every listener runs even if one throws. `RagInstance.on` therefore also returns an unsubscribe function. Reason: one tested implementation instead of two, and owners expose only `on`/`off`. (DESIGN §7.1; docs/architecture.md, Emitter)
- **All viewport tools share one contract and a registry.** Tools implement activate/deactivate, pointer down/move/up, keyDown, cancel (Esc), cursor and screen-space overlay drawing; the registry enforces the mode policy, maps hotkeys and opens a history gesture per press–release. Navigation is handled before tools. (DESIGN §5.5; docs/architecture.md, Tools)
- **Mode policy is a table in DESIGN §5.1** and a `MODE_POLICY` capability map in `js/modes.js`. Animate edits only the open clip (plus asset import), so rest-pose fields are read-only there and Manipulate only rotates; Simulate is read-only except selection, preview and playback. Changing mode cancels the current tool operation. Reason: DESIGN said "Edits affect: keys of the open clip" without saying which controls that disables. (DESIGN §5.1)
- **Hotkeys go through one dispatcher** with a fixed order (text fields and handled events ignored, then the focused viewport's tool, then the global table), and Space toggles Play/Pause on release only if no Space + drag pan happened; on a focused button Space keeps its native meaning. Reason: Space is both a pan modifier and the Play/Pause hotkey. (DESIGN §5.9; docs/architecture.md, Actions and hotkeys)
- **RagImporter is the `lib/` folder,** with `lib/ragimporter.js` as the only public entry. Hosts copy `lib/`; `demo/` imports only the entry; the editor may import internal `lib/` modules. Reason: schema, emitter, validation, serializer and evaluator must be shared, pure and testable, which one file would not allow at a reasonable size. (DESIGN §7, §8, §9)
- **Conformance with `docs/architecture.md` is checked:** automated by #66, as an item of the PR template, and by architect review of any PR that adds or changes a module. (docs/architecture.md, Conformance)
- **The header is a full-width toolbar with per-group alignment.** File, History and Playback sit on the left in that order, and Workspace (Window, Settings) sits at the right end. It has a single Tab stop with a roving tabindex. Unavailable actions use `aria-disabled` and stay focusable, and tooltips only show §5.9 hotkeys. Reason: "top center" did not say how the groups line up, and the shell built for #7 follows the usual editor layout, with document and playback actions near the tools and workspace settings out of the way. (DESIGN §5.3)
- **The viewport host stays `role="group"` until the viewport handles keys itself, then becomes `role="application"`.** Reason: screen readers use single-key hotkeys (V, B, M, F, Space…) for browse-mode navigation unless the focused region is an application, and an application role is not justified before there are keys to pass through. Its scope is limited to the viewport host. (DESIGN §5.4)
- **liquidfun.js is the doebi/liquidfun.js v1.1.0 Emscripten (asm.js) build**, reached through its `Box2D` namespace global with WebIDL accessors; RagImporter never assumes global `b2*` names. `RagImporter.configure` accepts `{ Box2D }` as well as `{ PIXI }`, both optional. It is the build the project owner uses, is self-contained and matches the reference demo byte for byte; injecting the namespace mirrors the PIXI handling and lets tests and module-based hosts supply it without a global. (DESIGN §7, §12)
- **PIXI.js is pinned to 8.21.0** after verifying `Assets`, `sortableChildren`/`zIndex` and `eventMode` + `pointermove`. (DESIGN §7, §12)
- **RagImporter targets LiquidFun + PIXI.js directly**, with no engine/renderer adapter layer. The project only targets this stack; an adapter layer can be added later if needed. (DESIGN §7)
- **Procedural joint control lives in RagImporter**; authoring (`aimAxis`) and preview live in the editor. Targets come from runtime data the editor cannot key. (DESIGN §4.8)
- **Shapes carry sprites** (offset, angle, scale, z), and the timeline can swap them through a discrete `sprite` channel. (DESIGN §2.3, §4.2)
- **The root is a world object** that parents everything and owns the global `strength`/`gain`/`damping` channels. These are 0–1 multipliers, never overrides, so a "dead" clip needs a single track. (DESIGN §2.1)
- **Springs are emulated with joint motors** (PD over motor speed, torque scaled by strength), because LiquidFun revolute joints have no spring. (DESIGN §3)
- **Layers:** the higher index wins; override by default, additive optional; no masks, since a clip only affects the tracks it has. (DESIGN §4.4)
- **Transitions** use per-clip `fadeIn`/`fadeOut`; a transition matrix is backlog. (DESIGN §4.1)
- **Grouping replaces FixedJoint**: a body can have several fixtures. (DESIGN §2.2)
- **The editor's Simulate mode uses RagImporter**, so preview equals production. (DESIGN §3, §5.1)
