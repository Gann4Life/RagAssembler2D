# Decisions

Dated log of design and technical decisions. Newest first. Each entry gives the decision, its reason and where it is specified.

## 2026-10-15
- **Gesture coalescing is restricted, and a net no-op gesture leaves no step.** A `set` merges into an earlier `set` on the same uid and path only when no op between them sets an overlapping path of that uid (`sprite` vs `sprite.offset`) or adds/removes a subtree containing it; otherwise it is appended. A gesture made only of `set` ops whose `previous` equals their `value` is discarded on end. Undo during a gesture only cancels it; Redo during a gesture does nothing; cancelled and discarded gestures keep the redo stack. Reason: unrestricted coalescing makes redo wrong when a gesture mixes whole-object and field sets on the same node, and an undo step that changes nothing looks broken to the user. (DESIGN §1; docs/architecture.md, Commands and undo)
- **History clears itself on the model's `reset` event instead of exposing `clear()`,** with the saved point at the new document for `new`/`load` and unreachable for `recover`. `dirty` stays true once the saved state can no longer be reached. Reason: callers could not get the order of `reset` and `clear` wrong (cancelling a gesture after a reset would apply ops to stale uids), and a recovered draft is by definition unsaved. (DESIGN §1; docs/architecture.md, Commands and undo)
- **History keeps the completed ops returned by each `tx` call and updates its stacks even when a model listener throws,** then rethrows; history calls made from inside `run` or a `change` listener throw. `execute` returns the value of `run`. Reason: `model.batch` throws after applying when a listener throws, so its return value is lost and history would drift from the model; re-entrant calls would nest batches. Returning `run`'s value lets create commands hand back the new uid without a side channel. (docs/architecture.md, Commands and undo)
- **The editor subscribes its cancellation listener to `modes` before anything else.** Reason: emitters run in subscription order, so Simulate start (#54) and other `mode` listeners never observe a half-done gesture. (DESIGN §5.1; docs/architecture.md, Editor composition)
- **The playhead resets to 0 when another clip is opened and is clamped to the clip length; a removed open clip or a reset returns to Edit mode.** Reason: DESIGN did not say what happens to the open clip when undo or delete removes it, or where the playhead goes between clips. (DESIGN §5.1; docs/architecture.md, Modes)
- **Hotkeys match `event.key` with exact modifiers, Cmd counts as Ctrl, a match always calls `preventDefault`, and only Undo, Redo and Next frame repeat.** Reason: `key` follows the user's layout, which is what the printed shortcut means; a disabled Save must still not open the browser's save dialog; repeating toggles (Space, tools, Delete) on a held key is never intended. (DESIGN §5.9; docs/architecture.md, Actions and hotkeys)
- **Disabled header actions state why:** "(not available yet)" when not built (not registered), "(not available in *Mode* mode)" when the mode policy refuses, nothing when only state disables them. `ActionRegistry` gains `has` and `reason`, and `actionTitle`/`setActionEnabled` take the reason. Reason: once Undo and Redo are built, "(not available yet)" on an empty stack would be false. (DESIGN §5.3; docs/architecture.md, Actions and hotkeys, Module map)
- **`setProps` refuses `id` paths and checks no types or ranges; multi-clip renames apply key-follows-name in order.** Reason: ids never change (DESIGN §1); types and ranges are already constrained by the inspector and reported by validation (#25), and drafts may be invalid; sequential application keeps keys of clips renamed together unique. (DESIGN §1, §4.1; docs/architecture.md, Commands and undo; docs/schema.md)
- **#10 builds modes as core state only.** Play, Pause, Next frame and Stop stay unregistered (disabled, "not available yet") until #54, and Edit/Animate switching gets its UI with the Timeline (#32). Reason: entering Simulate without a simulation, or Animate without a timeline, would show nothing; the state and policy are tested in Node now so later issues only wire them. (DESIGN §5.1, §5.3; docs/architecture.md, Modes, Editor composition)
- **The conformance tests read the layer classification from `docs/architecture.md`** (Core row of the layers table, `Pure` line of the components diagram, `js/` modules of the `tests/` dependency row) instead of a copy in code, and pure modules are checked by a static scan for `document`, `window`, `PIXI`, `Box2D` and `b2*` references rather than by loading them. Reason: one source for the layers, so editing the document changes what is enforced; a static scan reports file and line and needs no module to be importable yet. (docs/architecture.md, Conformance, Module map)
- **Model mutation calls are detected only when the receiver identifier ends in `model`;** aliases and destructured methods are not detected and are left to review. Reason: `reset` and `batch` are common method names (`dock.reset()`), and resolving aliases needs data-flow analysis a token scan cannot do; the receiver convention covers every call site the architecture describes with no false positives. (docs/architecture.md, Document model, Conformance)
- **Panel content modules may import nothing from `js/panels/`, `js/panels/layout.js` included,** although `layout.js` is core. Reason: panels are mounted by `js/main.js` into the element the dock gives them and must not depend on the dock or its layout model; the rule already said so for the dock modules, and the check makes it hold for any future panel file. (docs/architecture.md, Dependency rules, Conformance)
- **Every liquidfun.js verification test (`tests/liquidfun-*.test.js`) may load `vendor/liquidfun.js`,** not only `tests/liquidfun-api.test.js`. Reason: the #4 spike added `tests/liquidfun-contact-filter.test.js`, which loads it the same way; the rule had not been updated. (docs/architecture.md, Dependency rules)

## 2026-10-14
- **RagImporter owns one contact filter per world, and the host plugs into it.** Its `ShouldCollide` reimplements Box2D's default group/category/mask rule (bit fields `& 0xffff`), then the self-collision rule through a registry keyed by fixture pointer, then an optional host predicate set with `RagImporter.setContactFilter(world, predicate)`; a pair collides only if all three allow it. The filter is installed on the world's first `spawn` or `setContactFilter`, stays installed when the last instance goes, and is uninstalled and destroyed only by the new `RagImporter.releaseWorld(world)`, called right before the host destroys the world. Instances remove their registry entries before `DestroyBody`. The `groupIndex` fallback stays for builds without `JSContactFilter` and for hosts that opt out with `configure({ contactFilter: false })`. Reason: issue #4 spike (`tests/liquidfun-contact-filter.test.js`): a JS filter replaces the default rule, which the reimplementation matches; `userData` holds only an integer while the fixture pointer is stable and is what `ShouldCollide` receives; there is no `GetContactFilter`, so a host filter cannot be chained, only replaced; `SetContactFilter(null)` leaves no filtering at all, so uninstalling with the last instance would silently break the host's own category/mask rules; the cost is about +8 % step time for 20 humanoids. Hosts that need to collide pairs the default rule excludes cannot express that as an AND-ed predicate, hence the opt-out. Not a format change. (DESIGN §2.5, §7.1, §7.2, §7.4, §7.5, §8, §12; docs/architecture.md, Module map)
- **The liquidfun.js API surface is confirmed, and RagImporter follows fixed native-memory rules.** The pinned build exposes everything §3 and §7.2 need; motor, limit and angle methods exist only on the `b2RevoluteJoint` wrapper, so spawn casts each joint once with `Box2D.castObject` and stores it. Filter `maskBits` reads back signed and is masked with `& 0xffff`. The heap is a fixed 16 MiB that cannot grow, and exhausting it aborts the module, so: copied defs, shapes and filters are destroyed right after use; world-owned objects and getter results are never destroyed; `update()` and `sync()` allocate nothing and reuse a scratch `b2Vec2`; joints are destroyed before bodies. Reason: issue #5 spike, verified in Node by `tests/liquidfun-api.test.js`; a per-step leak would abort a running game within minutes. (DESIGN §3, §7, §7.2, §7.4, §12)
- **The pinned build supports a JS contact filter (`JSContactFilter` + `SetContactFilter`), but its integration stays open in issue #4,** and the `groupIndex` fallback stays specified until then. Reason: one filter per world, shared by instances and the host, replaces Box2D's default filtering, which the spike did not verify. (DESIGN §2.5, §12) *Superseded by "RagImporter owns one contact filter per world" above: issue #4 settled the integration and verified the default-rule replacement.*
- **When the window shrinks, the fill area gives way first, then the other areas shrink in proportion to their slack above their minimums, and only then does the workspace scroll.** The shrink is display-only; stored sizes come back when the window grows. Exception: resizing a handle stores the on-screen sizes of every fixed area of its split, except a folded Timeline. Reason: DESIGN said only the fill area changes, which leaves a dead end once the Viewport reaches its minimum; scrolling a workspace while side panels still have spare room is worse, and storing shrunk sizes would lose the user's layout on every small window. A resize, though, is the user choosing sizes; starting it from stale stored sizes made growing a shrunk pane shrink it. Matches the #8 implementation. (DESIGN §5.2; docs/architecture.md, Dock layout)
- **A resize handle resizes the area on its side away from its split's fill area; arrows move the handle spatially, Home/End give that area its minimum/maximum.** `aria-valuenow` is that area's size. Reason: "Home/End go to the minimum/maximum" did not say of what; this follows the WAI-ARIA window splitter pattern, where the value is the primary pane's size. (DESIGN §5.2; docs/architecture.md, Dock layout)
- **Center drops append the panel as the stack's last tab, previewed as the stack area plus an insertion caret after its last tab; tab bar drops insert at a caret.** Viewport edges accept split drops like stack edges. Reason: a center drop has no pointer-derived index, but the caret still tells where the tab will land; showing both answers "which stack" and "where in it". (DESIGN §5.2; docs/architecture.md, Dock layout)
- **Tools leave the dock and become a floating toolbar overlay inside the Viewport panel,** always visible, with no toggle and no Window menu entry; the overlay is specified now (placement, icons, states, keyboard) and built in its own issue, which also raises the Viewport minimum to 240 × 168 px and adds the framing inset. The Manipulate icon is a four-way move cross plus a rotation arc. Reason: product owner decision; a 72 px column cost workspace width for eight buttons, and tools act on the viewport, so they belong over it. (DESIGN §5.2, §5.3, §5.4, §5.5; docs/architecture.md, Module map, Dock layout)
- **Only the Timeline can be folded, and it starts folded.** The state is one layout-level flag, `timelineFolded`, not a stack property. It takes effect only while the Timeline is foldable: the active tab of its stack, and that stack a fixed area of a top-to-bottom split. Otherwise the fold control is hidden and the flag is kept. Activating any panel of the Timeline's stack, reopening or moving the Timeline, or dropping a tab into its stack expands it. Reason: product owner decision; a flag on a stack would have to follow the Timeline when it is dragged and be cleaned up when the stack is split, merged or removed, while one flag plus a derived "foldable" rule stays correct whatever the tree looks like, and folding a stack whose active tab is another panel would hide content the user did not ask to hide. (DESIGN §5.2; docs/architecture.md, Dock layout)
- **The stored layout moves to version 2 without migration.** Version 1 records are ignored with the usual console warning. Reason: removing `tools` and adding `timelineFolded` change the record, and no release shipped version 1, so a migration would only be untested code. (DESIGN §5.2; docs/architecture.md, Dock layout)
- **Tab bars win over workspace edge strips when dropping.** Reason: the 16 px strips covered the top half of the tab bars touching the workspace edges, and all of a folded Timeline's 28 px bar, which made tab drops there unreliable. The cost: no full-width bottom dock while a folded Timeline spans the bottom edge; the Timeline can be expanded first, or the panel docked on the Timeline's own edge. (DESIGN §5.2; docs/architecture.md, Dock layout)
- **The dock's DOM order follows the layout tree, so Tab order follows the layout,** and re-renders keep the focused element in place instead of recreating it. Overflowing tab bars scroll with the vertical wheel and fade 12 px on clipped edges. The active tab stays visible after resizes. Resize handles are named after the area they resize ("Timeline height") and grips have at least 3:1 contrast. Reason: dock review findings ranked high and medium; the lower-ranked ones go to separate issues. (DESIGN §5.2; docs/architecture.md, Dock layout)
- **Edit/Animate switching is hidden while the Timeline is folded,** because it lives in the Timeline clip selector; recorded as an open item, to be resolved before the Timeline panel is built. (DESIGN §5.1, §12)
- **Drops on the viewport use `stackId: 'viewport'`, and `'viewport'` is a reserved stack id** rejected by `validateLayout`. Reason: the viewport is a node, not a stack, and `Drop` needs one field to name either. (docs/architecture.md, Dock layout)
- **New stack ids are allocated above every id in the tree and in `closed`.** Reason: otherwise a closed panel whose stack was removed could reopen into an unrelated stack that reused the id. (docs/architecture.md, Dock layout)
- **Layout rules live only in `js/panels/layout.js`.** The dock reads the controlled child of a gutter from `Gutter.controlled` instead of re-deriving it, and `dropAt` takes the workspace size so the edge preview equals the result of `movePanel`. Reason: two copies of the same rule drift, and the preview must never lie about the drop. (docs/architecture.md, Dock layout)
- **Left/Right from an open menu move along the header through `focusAdjacentAction(header, button, key)` exported by `js/header.js`,** not through a synthetic `keydown` dispatched on the button. Reason: synthetic key events reach every key listener, including the future document-level `dispatchKey` (#10), and depend on listener order; an explicit call does not. (DESIGN §5.3; docs/architecture.md, Editor boot, Module map)
- **`js/storage.js` is tested under Node with a fake `localStorage`** installed on `globalThis` and restored after each test, as the dependency rules allow. Reason: the mapping of every storage failure to `missing`, `unavailable` or `parse` is the contract the dock and draft recovery (#29) rely on. (docs/architecture.md, Dependency rules, Module map)
- **The Viewport is a fixed panel.** It cannot be closed, tabbed or dragged and accepts no center drop; other panels dock on its edges, and it fills the workspace when everything else is closed. Reason: "all panels can be closed" would allow an editor with no viewport, and a single fixed fill area makes window resizing predictable. (DESIGN §5.2)
- **Every panel stack shows a tab bar, even with one panel,** and the tab is the title and the drag handle. Reason: one uniform drag source and title; a stack that hides its bar when alone would need a second drag affordance. (DESIGN §5.2)
- **The whole shared edge between panels is the resize handle,** with a grip at its middle as the visual mark. Reason: "handles sit at the middle of each edge" read as a small target; a full-edge hit area is what users expect and still keeps the grip as the cue. (DESIGN §5.2)
- **The layout is a tree of splits, stacks and the viewport,** sized in pixels with exactly one fill child per split, so window resizes only change the area holding the viewport. "Location" in §5.5–5.8 now means the default layout. Reason: the old wording fixed positions that docking makes movable. (DESIGN §5.2, §5.5–5.8; docs/architecture.md, Dock layout)
- **Reset layout has no confirmation and no undo, and layout changes are never undoable.** Reason: it touches no document data, is one menu click to reach and a few drags to rebuild, and the history must only hold document edits. (DESIGN §5.2; docs/architecture.md, Commands and undo)
- **Navigation keys stay in the focused composite widget.** While focus is in a toolbar, tab list, resize handle or open menu, its arrows, Home, End, Space, Enter and Esc do not trigger global hotkeys; widgets call `preventDefault`, which `dispatchKey` already skips. Reason: the header rule had to be repeated for every new widget; one rule covers them. (DESIGN §5.3, §5.9; docs/architecture.md, Actions and hotkeys)
- **The stored layout is a versioned record of its own** (`ragassembler.layout`, `version: 1`), independent of the `.rag.json` format version, validated on load and replaced by the default with a console warning when invalid. Reason: a corrupt or outdated layout must never block the editor, and layout changes must not bump the file format. (DESIGN §5.2; docs/architecture.md, Dock layout)
- **Layout logic is a pure core module, `js/panels/layout.js`,** separate from the DOM dock (`js/panels/dock.js`) and from browser storage (`js/storage.js`). Reason: normalize, validate, reopen and size distribution are the error-prone parts and must be unit-tested under Node; the same split already exists for `js/viewport/camera.js`. (docs/architecture.md, Layers, Module map)
- **`rovingIndex` takes an optional orientation** (`'horizontal'` by default, `'vertical'` for Up/Down), so tab lists and menus reuse it. Backward compatible. (docs/architecture.md, Module map)
- **A command's transaction is a `model.batch(fn)`.** Inside `fn`, each `tx` call is an `applyOps([op])` that applies immediately; the batch defers emission and emits one `change` (`do`) at the end, or reverts every op and emits nothing if `fn` throws. It returns `{ ops, changes }`; history records the ops and discards the entry when there are no changes. Batches do not nest. Undo, redo and cancel stay single `applyOps` calls. Reason: `run` must read its own writes and views must see one consistent change per command; keeping the revert logic in the model, which already has it for atomic `applyOps`, avoids a second, non-emitting mutation path and unbalanced begin/end calls. (docs/architecture.md, Document model, Commands and undo)
- **`applyOps` returns the completed ops,** with every derived field (`previous`, indexes, move `from`, removed snapshots, assigned uids) filled; these are what history records and inverts. Ops with no effect (a JSON-equal `set`, a `move` to the same slot) produce no change and no event, but are still returned. Reason: callers pass only intent, and inverse data comes from the one place that knows the state. (docs/architecture.md, Document model)
- **`reset` gives every node except the root a fresh uid,** and defaults to cause `new`; `applyOps` defaults to cause `do`. Reason: history and selection are cleared on reset, so no stale uid may alias a new node. (docs/architecture.md, Document model)
- **`nextId(prefix)` takes `b`, `f`, `j` or `s`** and returns `<prefix>_<n>` above every matching string seen in any prop in the session, references included; counters survive `reset` and never go down. "Never reused" therefore holds within a session, not across save and reload. Reason: a dangling reference in a draft or invalid file must never bind to a new object, and the editor has nowhere to persist a counter without a format change. (DESIGN §1; docs/architecture.md, Document model)
- **Model props never hold child collections.** A props key or `set` path naming a child collection of the node type is rejected; `defaultsOf` still returns list fields as `[]`, and snapshot builders move them to `children`. Reason: one place per datum; otherwise `props.fixtures` and the `fixtures` children could disagree and the serializer could not tell which to write. (docs/architecture.md, Document model; docs/schema.md, Code form)
- **`defaultsOf` leaves out fields whose default is set by the creating tool** (ids, names, `shape.vertices`, track `target`/`channel`, key `t`/`v`, event `t`, `meta.editorVersion`); `shape.type` is the variant when given. `CHANNELS` entries are `{ kind, unit, min?, max?, default, basePath }`. Reason: a placeholder default would hide a creator that forgot a field. (docs/schema.md)
- **The model enforces tree structure only,** not unique ids or clip keys, names, the reserved `root` id on other nodes, ranges or references. Those are command preconditions and validation (#25). Reason: drafts and invalid files must load into the model so Problems can report them. (docs/architecture.md, Document model)
- **Key-follows-name is applied by the rename command** (`setProps`, #10), in the same transaction as the rename, not by the model or the schema. (DESIGN §4.1; docs/schema.md, clip)
- **Shared helper modules are created by their first consumer.** `lib/geometry.js` lands with the first of #11, #20, #25, `js/model/queries.js` with the first of #13, #19, and `js/model/io.js` with #27, each with only the functions that issue needs. Reason: #9 had no consumer to test them against. (docs/architecture.md, Module map)
- **Undo uses command objects recorded as primitive operations, not model snapshots.** A command's `run(tx)` mutates the model only through `set`, `add`, `remove` and `move`; the history stores those ops with their inverse data, undo reverts them in reverse order and redo replays them. Reason: each op is also the change notification the views need, so the viewport, hierarchy and inspector update only what changed instead of diffing snapshots or rebuilding; a step costs only what changed, which keeps 200 steps cheap; redo replays the same ops, so ids and session uids stay identical; and inverses are mechanical, so commands never write hand-made `undo` code. (DESIGN §1; docs/architecture.md, Commands and undo)
- **One user operation is one undo step.** A compound command (delete with cascade, group, ungroup, duplicate, create + assign `rootBody`) is one transaction. Continuous edits merge through gestures: everything executed between press and release (or during an inspector scrub) is one entry, with `set` ops on the same path coalesced; Esc, tool switch, mode change or Undo during a gesture reverts it without leaving a step. Reason: time-window or per-command merge keys are fragile, and the gesture boundary is exactly what the user perceives as one action. (DESIGN §1, §5.6)
- **Every model node has a session uid.** Display objects, selection, history and change payloads use a numeric `uid` that is never serialized or reused in a session; file ids stay props and references keep using them. Reason: clips, tracks, keys and events have no file id, and one identity scheme for every node keeps the view maps and selection uniform. (docs/architecture.md, Document model)
- **The editor generates ids as kind prefix plus counter** (`b_3`, `f_3`, `j_3`, `s_3`), above any id of that prefix seen in the session; default names follow the same number (`body_3`, `box_3`, `joint_3`). Reason: ids must never be reused and must not depend on names, which users rename freely. (DESIGN §1; docs/schema.md)
- **One property schema in `lib/schema.js`, documented in `docs/schema.md`,** is the single source of field types, defaults, ranges/enums, units, editor-only flags and canonical key order for the model, validation, serializer and inspector. It lives in `lib/` because validation and the serializer do and `lib/` cannot import `js/`. Validation gains one generic error for missing fields, wrong types and out-of-range values, and `fixtures[].sprite` is the only optional field. Not a format break: no files exist yet and version stays 1. (DESIGN §6.2, §6.4)
- **Defaults that DESIGN left open are fixed in the schema:** box 0.5 × 0.5 m, circle radius 0.25 m, `angularDamping` 0, `editor.color` `#8c9eb5`, `pixelsPerMeter` 32, root name `ragdoll`, limits disabled at 0/0, and new keys `linear` (`step` for `sprite`). Motor defaults (80 N·m, 10 1/s, 0.5, 20 rad/s) come from the §6.1 example and are provisional until #52. (DESIGN §4.3; docs/schema.md)
- **`rootBody` is assigned automatically:** the first body created becomes `rootBody` while it is `null`, and deleting it moves it to the first remaining body (or `null`). A `null` `rootBody` is a validation error. Reason: DESIGN had no rule for an empty ragdoll or a deleted `rootBody`, and both cases occur in the first minutes of use. (DESIGN §2.1, §5.6, §6.4)
- **A clip key follows its name while it equals the generated slug,** instead of a stored "edited by hand" flag. Reason: it needs no extra field and survives save/load. Tracks with no keys are valid and have no effect, so "+ Track" can create an empty track. (DESIGN §4.1, §4.3; docs/schema.md)
- **Model changes are batched per transaction and the viewport flushes once per frame.** The model emits one `change` event (list of add/remove/set/move) per commit, undo, redo or cancelled gesture, and `reset` on New/Load/recover; the scene keeps PIXI display objects keyed by uid and only updates dirty entries. Reason: views always see a consistent model after compound commands, and long drags cost one redraw per frame. (docs/architecture.md, Change notifications, View sync)
- **One `Emitter` class in `lib/emitter.js`** serves the editor core and `RagInstance`: synchronous, in order, one payload, `on` returns an unsubscribe function, every listener runs even if one throws. `RagInstance.on` therefore also returns an unsubscribe function. Reason: one tested implementation instead of two, and owners expose only `on`/`off`. (DESIGN §7.1; docs/architecture.md, Emitter)
- **All viewport tools share one contract and a registry.** Tools implement activate/deactivate, pointer down/move/up, keyDown, cancel (Esc), cursor and screen-space overlay drawing; the registry enforces the mode policy, maps hotkeys and opens a history gesture per press–release. Navigation is handled before tools. (DESIGN §5.5; docs/architecture.md, Tools)
- **Mode policy is a table in DESIGN §5.1** and a `MODE_POLICY` capability map in `js/modes.js`. Animate edits only the open clip (plus asset import), so rest-pose fields are read-only there and Manipulate only rotates; Simulate is read-only except selection, preview and playback. Changing mode cancels the current tool operation. Reason: DESIGN said "Edits affect: keys of the open clip" without saying which controls that disables. (DESIGN §5.1)
- **Hotkeys go through one dispatcher** with a fixed order (text fields and handled events ignored, then the focused viewport's tool, then the global table), and Space toggles Play/Pause on release only if no Space + drag pan happened; on a focused button Space keeps its native meaning. Reason: Space is both a pan modifier and the Play/Pause hotkey. (DESIGN §5.9; docs/architecture.md, Actions and hotkeys)
- **RagImporter is the `lib/` folder,** with `lib/ragimporter.js` as the only public entry. Hosts copy `lib/`; `demo/` imports only the entry; the editor may import internal `lib/` modules. Reason: schema, emitter, validation, serializer and evaluator must be shared, pure and testable, which one file would not allow at a reasonable size. (DESIGN §7, §8, §9)
- **Conformance with `docs/architecture.md` is checked:** automated by #66, as an item of the PR template, and by architect review of any PR that adds or changes a module. (docs/architecture.md, Conformance)
- **The header is a full-width toolbar with per-group alignment.** File, History and Playback sit on the left in that order, and Workspace (Window, Settings) sits at the right end. It has a single Tab stop with a roving tabindex. Unavailable actions use `aria-disabled` and stay focusable, and tooltips only show §5.9 hotkeys. Reason: "top center" did not say how the groups line up, and the shell built for #7 follows the usual editor layout, with document and playback actions near the tools and workspace settings out of the way. (DESIGN §5.3)
- **The viewport host stays `role="group"` until the viewport handles keys itself, then becomes `role="application"`.** Reason: screen readers use single-key hotkeys (V, B, M, F, Space…) for browse-mode navigation unless the focused region is an application, and an application role is not justified before there are keys to pass through. Its scope is limited to the viewport host. (DESIGN §5.4)
- **liquidfun.js is the doebi/liquidfun.js v1.1.0 Emscripten (asm.js) build**, reached through its `Box2D` namespace global with WebIDL accessors; RagImporter never assumes global `b2*` names. `RagImporter.configure` accepts `{ Box2D }` as well as `{ PIXI }`, both optional. It is the build the project owner uses, is self-contained and matches the reference demo byte for byte; injecting the namespace mirrors the PIXI handling and lets tests and module-based hosts supply it without a global. (DESIGN §7, §12)
- **PIXI.js is pinned to 8.21.0** after verifying `Assets`, `sortableChildren`/`zIndex` and `eventMode` + `pointermove`. (DESIGN §7, §12)
- **RagImporter targets LiquidFun + PIXI.js directly**, with no engine/renderer adapter layer. The project only targets this stack; an adapter layer can be added later if needed. (DESIGN §7)
- **Procedural joint control lives in RagImporter**; authoring (`aimAxis`) and preview live in the editor. Targets come from runtime data the editor cannot key. (DESIGN §4.8)
- **Shapes carry sprites** (offset, angle, scale, z), and the timeline can swap them through a discrete `sprite` channel. (DESIGN §2.3, §4.2)
- **The root is a world object** that parents everything and owns the global `strength`/`gain`/`damping` channels. These are 0–1 multipliers, never overrides, so a "dead" clip needs a single track. (DESIGN §2.1)
- **Springs are emulated with joint motors** (PD over motor speed, torque scaled by strength), because LiquidFun revolute joints have no spring. (DESIGN §3)
- **Layers:** the higher index wins; override by default, additive optional; no masks, since a clip only affects the tracks it has. (DESIGN §4.4)
- **Transitions** use per-clip `fadeIn`/`fadeOut`; a transition matrix is backlog. (DESIGN §4.1)
- **Grouping replaces FixedJoint**: a body can have several fixtures. (DESIGN §2.2)
- **The editor's Simulate mode uses RagImporter**, so preview equals production. (DESIGN §3, §5.1)
