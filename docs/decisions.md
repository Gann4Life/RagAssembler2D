# Decisions

Dated log of design and technical decisions. Newest first. Each entry gives the decision, its reason and where it is specified.

## 2026-10-15
- **Manipulate merges into Select (#128): Select (V) selects and transforms, Select Box (B) stays marquee-only, Pose (P) is unchanged, and the Manipulate tool is removed outright.** The `manipulate` row leaves `TOOL_SPECS` (so its action, toolbar button and `M` hotkey row go with it), `tool.manipulate` leaves `MODE_POLICY`, `M` is left free, and `js/tools/manipulate.js` is deleted; its target and pivot functions move unchanged to a new core `js/tools/manipulation.js`. No `M` alias of `V`. Reason: owner-confirmed design; switching between V and M for every limb was the main friction #17 left, and an alias would keep a second name and hotkey for one tool in the toolbar, the tooltip texts and §5.9, while freeing `M` costs nothing before 1.0. The toolbar shrinks to seven buttons: one column 40 × 265 px, two-column threshold 281 px, two columns still 76 × 149. Supersedes the 2026-10-15 entries "A drag in Select also draws a selection box (any modifiers)" for drags that start on an object in Edit mode, and "Manipulate acts on a target derived from the selection" for where the selection changes (now at the latch, below). (DESIGN §5.1, §5.5, §5.9; docs/architecture.md, Tools, Modes, Module map)
- **Select press resolution: handle, then object, then empty space.** In Edit mode a drag that starts on an object moves (the whole target when the topmost hit belongs to it; otherwise the topmost hit is selected alone at the 4 px latch, not at the press, and its target moves); a drag on empty space draws a selection box; a click keeps every #13 rule, ALT cycling included. A drag always starts from the topmost hit (ALT then means "bodies only"), and SHIFT and CTRL never change what a drag selects. In Animate (until #125) and Simulate mode every drag draws a box. Reason: selecting at the latch keeps click semantics exact (an ALT click on a stack must not select at the press), while a drag still grabs what is under the pointer; keeping the drag's selection fixed matches #17 and leaves SHIFT and CTRL to clicks and boxes. A box that starts on top of objects is what Select Box is for. (DESIGN §5.5)
- **Transform gizmo geometry, world-aligned and constant-size:** X arrow `#e0524f` and Y arrow `#58b85c` (the grid axis colors) from 16 to 56 px, a `#f2c94c` 12 px free-move square in the quadrant between them (16–28 px), a `#5b9cf5` rotation ring of 72 px radius around them, and a pivot mark in `#d8dade` (a cross in Center mode, a ring with a dot in Last selected mode). Hit areas: the square grown by 2 px, 6 px around arrows and ring, and **nothing within 12 px of the pivot**. Hover and active handles turn white and 1 px wider, and suppress object hover. The ring is shown only when rotation can change something (root, any body, two or more joints). Reason: owner-confirmed colors and handle set; the free-move square is offset instead of centered because the pivot is usually a parent joint anchor, so a dead zone of the root's 12 px hit radius keeps the joint or root at the pivot pressable as an object, which settles #127 (the gizmo stays grabbable beside joint gizmos and never covers the one it sits on). Matching the grid axis colors ties each arrow to its world axis. (DESIGN §5.4, §5.5)
- **Handle hit priority: gizmo square, then point handles (`aimAxis` tip #24, sprite handles #24, resize handles #129, 8 px each), then the X and Y arrows, then the ring; joints, the root and shapes after every handle.** Handles draw in reverse order; the gizmo never moves to make room for point handles. Reason: point handles are small and specific, while arrows and the ring stay grabbable along most of their length, so a point handle may sit on them; the default `aimAxis` (bodyB's +X) would otherwise always hide under the X arrow. The square is too small to share, so it stays first. This is the slot #129 fits into; its own layout is not specified here. (DESIGN §5.4, §5.5)
- **Pivot rules:** one object uses its own pivot (root position; one body's parent joint anchor when placed, else its origin; one joint's anchor); several objects use the pivot mode: Center = mean of the target bodies' origins and placed joint anchors, Last selected = the pivot of the target object that the last selection entry maps to (a shape maps to its body). CTRL forces a body's origin wherever a parent anchor would be used and changes nothing in Center mode. The pivot follows a move and stays fixed during a rotation. Reason: owner-confirmed; "last selected" needs a deterministic definition, and the selection order is the only one the editor has. (DESIGN §5.5)
- **Z toggles the pivot mode through a `pivot-mode` action and a §5.9 hotkey, not a tool key; the mode is an editor setting `gizmo.pivot` (`'center'` default), persisted per browser, not in the Settings popover, unavailable during a drag.** Z does not clash with §5.9: modifiers match exactly, so Z and Ctrl+Z are different keys; the one interaction is that CTRL held for the body origin turns Z into Undo, which aborts the drag, and §5.9 says so. Reason: a tool key would only work with the viewport focused, unlike every other §5.9 key; the setting store already gives persistence, validation and events (the overlay redraws on `settings`) at no new cost, and the record stays version 1 because a missing field restores to its default. Changing the pivot mid-drag would need a second sweep-restart rule, so it is simply refused. (DESIGN §5.3, §5.4, §5.5, §5.9; docs/architecture.md, Tools)
- **Moves snap a reference point: the pressed object's point for object drags (#17), the pivot for gizmo drags; an arrow keeps the other component at 0 and snaps only its own axis. Rotation SHIFT snaps the root's angle, one body's root-local angle, or else the rotation itself.** Reason: the gizmo user aligns the pivot, the object user aligns what they grabbed; snapping the cross axis of an arrow drag would jump it off its line; several bodies have no single angle to round. (DESIGN §5.4, §5.5)
- **Multi-selection rotation needs no new command:** `startRotation` applies one `rotationAbout(pivot, θ)` through the existing `transformParts`/`placeParts` to the union of the targets' subtrees, which is rigid by construction. This replaces the 2026-10-15 decision that left multi-body rotation out of v1, and the #17 rotate knob with its sizes (`rotateHandle`, `rotateKnob`). Reason: a shared pivot was the missing piece, and the pivot mode supplies it. (docs/architecture.md, Tools, Commands and undo)
- **Drag readout:** `Δx: 12.0 px  Δy: -3.5 px` (document pixels at `pixelsPerMeter`, world axes) or `Δθ: 15.0°` (applied rotation, counter-clockwise positive), one decimal, 16 px right of and below the pointer, kept inside the viewport, styled like the name labels. Tools stay PIXI-free: the `Tool` contract gains `readout()` and `handleAt(screen)` (both default to `null`), the registry forwards them, and `js/viewport.js` draws the text with a pooled `PIXI.Text` and suppresses object hover over handles. Reason: the owner asked for a live readout and handle hover; the tool overlay only receives a `PIXI.Graphics`, which cannot draw text, and hover is computed by the viewport, which cannot know tool handles otherwise. (DESIGN §5.4, §5.5; docs/architecture.md, Tools, Module map)
- **Module split for #128:** core `js/tools/manipulation.js` (target, pivots, `startMove`/`startRotation` drag sessions shared by object drags and handles) and core `js/tools/transform-gizmo.js` (pure screen-space layout, hit test, drawing, readout text); `js/tools/select.js` gets its own lifecycle and keeps `clickTarget`/`applyClick`, reusing `boxAabb`/`applyBox` from `js/tools/select-box.js`; `js/commands/transform.js` is unchanged. All new modules fall under `js/tools/*` in the Core row, so the layer table does not change. Reason: the gizmo geometry is a pure table that must be tested without a tool; the drag sessions are what #125 (Animate ring), #24 (sprite edit) and #129 extend, so they cannot live inside the Select closure. (docs/architecture.md, Module map, Tools)
- **Animate mode in #128: Select only selects (as in Simulate), with no gizmo; #125 adds the ring alone, into the parent joint's `angle`.** DESIGN §5.5 already specifies the #125 behavior (one body with a parent joint, ring only, CTRL, ALT and pivot mode inert). Reason: Animate rotation needs the FK pose and key commands, as in the 2026-10-15 #17 scope decision. (DESIGN §5.1, §5.5; docs/architecture.md, Tools)
- **Backspace is not a Delete key; Del is the only one.** §5.9 is unchanged. Reason: owner decision; Backspace edits text in the search field and inspector, and a second, easily hit key for a destructive action without confirmation adds risk for no gain on keyboards that have Del. (DESIGN §5.6, §5.9)
- **When Manipulate drags a body with its joint subtree, the anchor of the joint at the subtree's edge (to the parent body, which stays) travels with the moved body.** Owner decision, for #17; recorded now so the Hierarchy's body → joint → child model and Manipulate agree on which side owns that joint. Reason: the anchor is where the child hangs from, so it stays on the child's shape; leaving it behind would put it outside both shapes after nearly every move. (DESIGN §5.5)
- **The Delete button's tooltip gives "the ragdoll root cannot be deleted" when only the root is selected,** an explicit exception to §5.3's rule that state-only unavailability shows no reason. The mode reason wins outside Edit mode, and a gesture shows none. Reason: a selected object that cannot be deleted is otherwise unexplained, unlike Undo with nothing to undo. (DESIGN §5.3, §5.6; docs/architecture.md, Hierarchy and deletion)
- **Hierarchy presentation from the `ui-ux-analyst` review, accepted whole:** icon-only trash Delete button right of a single Add menu button (items "Add shape", "Add joint"; focus returns to Add; a disabled Add does not open; Add clears an active search first so the new row shows); the Unlinked row as a `--warning` triangle with a muted label, toggled by double click; loop leaves with a muted "loop" badge and "→ *bodyB*" (`HierarchyItem.loopTo`, never searched); an `--error` "unassigned" badge; double click on an object row selects and frames it; ArrowDown in the search field enters the tree without selecting; external selection changes make the last revealed row the roving stop without moving DOM focus; dimmed ancestors use the muted text color, not opacity; row `aria-label`s that spell out kind, id match, loop target and unassigned state, plus a visually hidden key description on the tree. None contradicts §5.6. Reason: the review targets the cases the first draft left visual-only (marks, the group row, dimming) or ambiguous (focus after Add, entering the tree from search), and the loop target saves a trip to the inspector to find which body a loop closes to. Hovering a row to highlight its object in the viewport is out of #19 (follow-up). (DESIGN §5.6; docs/architecture.md, Hierarchy and deletion)
- **`js/tooltip.js` gains a `placement` option (`'right'` default, `'below'` for panel toolbars), `js/menu.js` names its menu from the button's `aria-label` before its text content, and `css/editor.css` adds `--error` (#e5484d) and `--warning` (#f5a524) to `:root`.** Reason: a tooltip to the right of a toolbar button at the top of a right-side panel covers its neighbour or is clamped against the window; an icon or menu button's visible text is not its name; error and warning colors will be shared by the Problems panel and the inspector, so they are tokens from the first use. Public signatures stay backward compatible. (docs/architecture.md, Module map, Hierarchy and deletion)
- **Deleting the remaining shapes of a body deletes the body, with the full body cascade (its joints, the tracks of its shapes and joints, `rootBody` reassignment).** Reason: a body without shapes is a validation error that blocks Save, has no hit area and cannot be selected in the viewport, and in the UI a shape and its body are one thing (§2.2: drawing a shape creates its body); leaving an empty body behind after Del would force a second, Hierarchy-only deletion. Confirmed by the owner on 2026-10-15. (DESIGN §2.2, §5.6; docs/architecture.md, Hierarchy and deletion)
- **Delete asks for confirmation only when it would remove animation tracks; every other deletion is immediate, and Undo is the safety net.** This narrows §5.6, which asked for a confirmation on every body deletion. Reason: in the viewport nearly every Del removes a body (the last shape of its body) and often joints, so the old rule would put a dialog in the most common edit; joints are visible and come back exactly with one Undo, while tracks are invisible in Edit mode and can span several clips. No built path can create tracks yet, so #19 computes `DeletionPlan.confirm` and tests it but ships no dialog; a follow-up builds the shared confirmation dialog (also for New, #27) before Load (#27) or tracks (#33) merge. Confirmed by the owner on 2026-10-15. (DESIGN §5.6; docs/architecture.md, Hierarchy and deletion)
- **Del deletes bodies, shapes and joints from the object selection; the root is skipped (the rest is deleted, and Delete is unavailable with only the root selected), and sprite assets and clips are left to their own panels.** With the timeline focus, Del belongs to the timeline issue (#34). Reason: the root can never be removed and blocking a whole deletion because the root is also selected would be surprising after a multi-selection; asset deletion has its own in-use rule (§5.6 Assets) and clip deletion its mode rules (§5.1, §5.8), which #19 does not build. (DESIGN §5.6; docs/architecture.md, Hierarchy and deletion)
- **`deleteObjects(uids)` computes its `DeletionPlan` inside `run`, removes tracks, joints, lone shapes and bodies with one `remove` op each, then sets `rootBody`; the plan is a separate pure function, `deletionPlan(model, uids)`.** Reason: computing in `run` means the plan can never be stale, while redo re-applies the recorded ops and never calls `run`, so ids and uids come back identical; every `remove` op carries its subtree snapshot and index, so undo is exact with no new history feature; a separate plan lets the action decide enablement and confirmation without executing anything. (DESIGN §1, §5.6; docs/architecture.md, Hierarchy and deletion)
- **Hierarchy Add runs actions (`add-shape`, `add-joint`) registered in `js/editor.js`, like `delete`;** Add shape reuses `createShapeBody` (box of the schema default size at root-local (0, 0), angle 0, label "Add shape"), and Add joint reuses `createJoint`, which now accepts `bodyA` and `bodyB` both `null` (an unassigned joint). Each selects what it created. Reason: one command per kind of creation keeps ids, names and undo identical to the tools; actions give Add and Delete the mode reason and the no-commands-in-a-gesture rule for free; `null` bodies were already allowed in the model and in drafts (schema.md). (DESIGN §5.6; docs/architecture.md, Hierarchy and deletion, Commands and undo; docs/schema.md)
- **Every body row shows its shapes, also single-shape bodies; loop joints are leaves under their `bodyA`; unlinked parts are joint trees of their own under the Unlinked group, rooted at their first body in `bodies` order, followed by unassigned joints.** Unlinked cycles are marked "loop" in the Hierarchy too, although validation only reports loops reachable from `rootBody`. Reason: two-way selection sync needs a row for every shape a viewport click can select ("grouped bodies expand" left single-shape bodies without one); the owner requires every created object, including an unassigned joint from Add, to appear; a loop joint has no child body of its own, so a leaf under its parent side is the only place that keeps the body → joint → child order; a cycle drawn without a marker would look like a joint with a missing child. (DESIGN §5.6; docs/architecture.md, Hierarchy and deletion)
- **Hierarchy selection follows the viewport's modifiers (click selects only, SHIFT toggles, CTRL removes), keyboard focus moves select (SHIFT adds, CTRL moves only), Space toggles, and there is no type-ahead.** Reason: one set of modifiers for selecting the same objects in two places; selection-follows-focus is the WAI-ARIA multi-select tree alternative that suits an editor where the inspector shows the selection; type-ahead would steal the single-letter tool hotkeys and F, and the search field covers finding by name. Range selection (file-manager SHIFT + click) is not in v1. Reviewed and accepted by `ui-ux-analyst` (CTRL + Space also toggles). (DESIGN §5.6, §5.9)
- **Hierarchy search is a case-insensitive subsequence match on name or id that keeps ancestors (dimmed) and starts expanded, with a temporary expansion state discarded when the query changes.** Reason: DESIGN said "fuzzy" without a rule; a subsequence match is the simplest fuzzy rule with predictable highlights; keeping the user's expansion state separate means a search never rearranges the tree they come back to. (DESIGN §5.6; docs/architecture.md, Hierarchy and deletion)
- **The Hierarchy splits into core `js/model/hierarchy.js` (tree items, Unlinked group, marks, fuzzy search, visible rows) and `js/tree-nav.js` (tree key moves), and UI `js/panels/hierarchy.js`; `js/model/queries.js` exports `jointEdges` and gains `referencesTo`.** Reason: panel content modules may not import from `js/panels/`, so the pure tree model cannot live next to the panel; everything that decides what is shown, focused or deleted is then tested under Node; exporting the existing edge helper keeps one edge rule for `jointTree` and the Hierarchy forest. `js/tree-nav.js` mirrors `js/roving-focus.js` and is added to the Core row. (docs/architecture.md, Dependency rules, Module map, Hierarchy and deletion)
- **Hierarchy as built (#19) differs from the spec in small ways:** the Add button shows the visible text "Add" with a chevron (still named by `aria-label`) and opens its menu on ArrowDown (first item) and ArrowUp (last item); the tree ignores Alt-modified keys; Shift+Space also toggles; the focused-row outline is drawn on `:focus-visible`; collapsing an ancestor of the roving row moves the roving stop to the collapsed row; and the dock section keeps `tabindex="0"`, so the panel is one Tab stop before the search field. The last one is open for the architect: either keep it (a landmark stop that every dock panel shares) or drop it for panels that hold focusable content. Reason: each follows from using the controls as built (text button, native key defaults, existing dock markup) and none changes what the spec decides. (DESIGN §5.6; docs/architecture.md, Hierarchy and deletion)
- **The Manipulate rotation sweep restarts on a CTRL change only when CTRL actually moves the pivot.** A body without a parent joint (or with an unplaced anchor) has the same pivot with and without CTRL, so toggling CTRL leaves its swept angle untouched. Reason: DESIGN §5.5 says the angle is measured again from the press point "when CTRL changes the pivot"; restarting without a pivot change would reset the sweep for nothing. (DESIGN §5.5; docs/architecture.md, Tools, Manipulate)
- **Manipulate acts on a target derived from the selection: the root alone when it is selected; otherwise the selected bodies, the bodies of the selected shapes and the selected joints.** A press on a handle drags it; a press on a hit that belongs to the target drags the whole target; a press on any other hit selects only that object at the press and drags it; a click on empty space clears the selection. Modifiers never change the selection, and an aborted drag keeps the selection made at its press. Reason: the owner decided that a selected shape moves its body (#17 issue comment); press-to-select avoids switching between V and M for every limb, while SHIFT, CTRL and ALT stay free for snapping, pivot and "only this body"; selection is not undoable and not part of the operation. Pending owner confirmation of press-to-select. (DESIGN §5.5; docs/architecture.md, Tools)
- **Parent joint and subtree are defined in the model: a linked body's parent joint is its `jointTree` tree joint; an unlinked body's is the first joint in `joints` order that has it as bodyB; the subtree is every body whose chain of parent joints leads to the body.** `js/model/queries.js` gains `parentJoints(model)` and `bodySubtree(model, bodyUid, parents?)` only. Reason: subtrees must work before a limb is linked to `rootBody` (most limbs are built first, and the Hinge tool then makes the earlier body bodyA); on linked bodies the definition equals the Hierarchy tree, and loop joints never define parenthood. Two small functions keep the change local next to the concurrent #19 additions. (DESIGN §2.4; docs/architecture.md, Joint graph)
- **A joint anchor moves with a moved part when the body it is the parent joint of moves, or when both its bodies move; selected joints' anchors move too.** So a limb carries its own attachment point, and ALT on a forearm carries the elbow but not the wrist. Reason: the anchor is where the child hangs; leaving it with the parent would make a moved limb hang from a point outside it, and both choices are equally valid physics. Pending owner confirmation. (DESIGN §5.5; docs/architecture.md, Commands and undo)
- **A move translates everything by one vector, chosen so that the pressed object's point (root position, the pressed shape's body origin, the pressed joint's anchor) lands on the grid.** Reason: snapping each body separately would deform the subtree; the pressed object is the one the user aligns. (DESIGN §5.4, §5.5)
- **Rotate knob: 5 px knob 40 px from the pivot along the root's or body's +X, with a line and a 4 px pivot cross; hit within 8 px; shown for the root or exactly one body without joints.** The body pivot is its parent joint's anchor when placed, else its origin; CTRL forces the origin, ALT rotates only the body, SHIFT snaps the root angle or the body's root-local angle to 15°, all read live; the swept angle is unwrapped past half a turn and restarts when CTRL changes the pivot. Reason: §5.5 named a rotate handle without geometry; a knob along +X shows the angle and its 15° steps while turning, and stays off the limb's long axis for boxes drawn along it; "center" is read as the body origin, which is the drawn shape's center (§2.2) and needs no mass; several bodies have no common pivot, so multi-body rotation is left out of v1; ALT keeps one meaning ("only this body") across move and rotate. (DESIGN §5.4, §5.5; docs/architecture.md, Tools, Module map)
- **`js/commands/transform.js` exposes `manipulationParts`, `transformParts`, `rotationAbout` and one command, `placeParts`, which sets absolute positions, angles and anchors and skips unchanged values; root moves and rotations, and `aimAxis`, use `setProps`.** The planned `moveRoot`, `moveBodies`, `rotateBody`, `moveAnchor` and `setAimAxis` are dropped; `editSprite` stays for #24. Each drag step is computed from the values captured at the press, and entries outside the active set (ALT) are written back at their start values. Reason: absolute values from the press coalesce into one undo entry per path and leave no step for a drag back to the start; deltas on the current model would accumulate across steps; one rigid-transform command covers move, rotate, ALT and joint-only drags. (docs/architecture.md, Commands and undo, Module map)
- **#17 scope: Edit mode moves (root, bodies with subtrees, joint anchors) and the rotate knob. #24 keeps the `aimAxis` handle and sprite edit; Animate rotation into the parent joint's `angle` comes after FK (#36) and key commands (#39).** Until then Manipulate in Animate mode only selects. Reason: moving selected joint anchors is the same rigid transform as bodies and costs nothing extra, while Animate rotation needs the FK pose and key writing, which do not exist yet. #24's issue text should drop "joint anchor"; the Animate rotation needs an issue. (DESIGN §5.5; docs/architecture.md, Tools)
- **The tool overlay also redraws on `selection`, `mode`, model `change` and `reset` events** (`js/viewport.js`). Reason: Manipulate handles follow the selection and the document (undo, inspector edits), which the registry's `invalidateOverlay`, `camera` and `tool` triggers do not cover; one rule in the viewport serves later handle tools (#24, #38). (docs/architecture.md, Tools, Module map)
- **bodyA is chosen by joint distance to `rootBody`, counted over undirected joints; unlinked bodies count as farthest, and ties go to the body earlier in `bodies` order.** Creating a joint never reorients existing joints. The rule lives in `orderJointBodies` (`js/model/queries.js`), used by the Hinge tool; `createJoint` takes bodyA and bodyB already ordered and never reorders. Reason: DESIGN said "closer to `rootBody`" without a metric or a tie rule, and most joints are drawn before their limb is linked (both unlinked); `bodies` order is deterministic, model-only, and matches the usual build order from the torso outward and the hit order (later bodies are on top, so the topmost shape usually becomes the child). Counting joints in either direction keeps the tree connected when a user has swapped a joint in the inspector. Not a format change. (DESIGN §2.4, §5.5; docs/architecture.md, Joint graph)
- **`js/model/queries.js` is created by #16 with `jointTree`, `jointBetween` and `orderJointBodies`;** `jointTree` is a breadth-first search from `rootBody` that visits edges in `joints` order, so depths are shortest joint counts and the spanning tree, and hence which joint is a loop joint, is deterministic. Loop joints are only reported among bodies reachable from `rootBody`. Reason: the Hinge tool needs depths before #13 or #19 land; BFS gives the "closer" metric directly; an unlinked part is already reported as unlinked, and flagging its internal cycles as loops would double-report it. (DESIGN §2.4; docs/architecture.md, Joint graph, Module map)
- **The Hinge tool refuses a press with fewer than two bodies under the pointer, or on a pair already joined in either order; a joint that closes a longer loop is allowed and becomes a loop joint.** A refused press changes nothing and is signalled beforehand by a `not-allowed` cursor while hovering. The same-pair refusal is also a `createJoint` precondition. Reason: owner priority is that joining two bodies works reliably; a second hinge between the same pair is never useful (two anchors weld them, one anchor is redundant) and usually comes from a repeated or double click, while longer loops (two hands on one object) are valid physics that DESIGN already supports with a warning. The cursor is the only pre-press feedback because tools receive no pointer-leave event, so an idle overlay preview would stay behind when the pointer leaves the viewport. (DESIGN §5.5; docs/architecture.md, Tools, Commands and undo)
- **Hinge bodies come from the pointer position, the anchor is the grid-snapped press point.** Reason: the bodies the user sees under the cursor are the ones joined; hit testing at the snapped point could pick other bodies, or none, at a spot the user did not point at. A snapped anchor outside both shapes is reported by the existing validation warning. (DESIGN §5.4, §5.5)
- **Hinge limit drag: θ is the screen distance from the anchor's current screen position, 1 px = 1°, rounded to whole degrees, clamped to 0–180°, SHIFT rounds to 15°; a drag ending at θ = 0 creates a pin; a click creates a pin.** The press uses the same 4 px drag latch as Circle and Box. Reason: whole degrees give clean inspector values; measuring from the anchor's current screen position keeps θ equal to the drawn arc after a pan or zoom mid-drag; SHIFT already means 15° angle snap everywhere else; a zero-width enabled limit would lock the joint, which nobody means by dragging back. (DESIGN §5.4, §5.5; docs/architecture.md, Tools)
- **The Hinge preview is the joint gizmo of §5.4 in the hover color (circle, needle along the zero direction, arc once θ > 0), computed with `jointZeroAngle` from world values.** Reason: the needle points to bodyB's origin, so the user sees which body becomes the child before releasing, and the preview is exactly the gizmo the joint gets after creation. (DESIGN §5.4, §5.5; docs/architecture.md, Tools)
- **`createJoint({ bodyA, bodyB, anchor, limits? })` in `js/commands/create.js` takes body uids and a root-local anchor, appends one joint with one `add` op, leaves `rootBody` untouched, and returns the joint uid.** Preconditions (non-body or equal uids, an already joined pair, a non-finite anchor, limits not around 0) throw before an id is allocated. Reason: same shape as `createShapeBody`, exact undo and redo through the `add` inverse; uids match the rest of the command API, and the command stores file ids as references are stored. (DESIGN §2.4; docs/architecture.md, Commands and undo; docs/schema.md)
- **Select and Select Box select shapes, joints and (by click only) the root; a click on a shape selects the shape, never its body.** Bodies are selected from the Hierarchy (#19). Reason: confirms the existing §5.4 hit rule; bodies have no hit area of their own, and the tools then need no body resolution or `js/model/queries.js`. Confirmed by the owner on 2026-10-15: Manipulate (#17) moves the body of a selected shape. (DESIGN §5.4, §5.5; docs/architecture.md, Tools)
- **Click semantics:** the target is the topmost hit; ALT picks the hit just below the topmost selected hit, wrapping, so repeated ALT + clicks cycle through overlapping objects. No modifier selects only the target, SHIFT toggles it, CTRL removes it (CTRL wins); an empty click clears the selection without modifiers and does nothing with them. Reason: SHIFT toggle was already specified; CTRL is free in the selection tools and gives a remove that a toggle cannot express for boxes; ALT was unused and a joint anchor (8 px) otherwise always hides the shapes under it. Plain clicks never cycle, so clicking a selected object keeps it. (DESIGN §5.5; docs/architecture.md, Tools)
- **Selection boxes take shapes entirely inside them and joints whose anchor is inside, never the root; none replaces, SHIFT adds, CTRL removes (CTRL wins), modifiers read at the release.** Containment is tested with `shapeBounds` against the world box, which is exact for an axis-aligned box. Reason: containment avoids grabbing large background shapes when boxing limbs of a dense ragdoll and needs no new intersection geometry; the root contains everything and would turn every box into "select the ragdoll", which Manipulate and Group would then have to untangle. Intersect mode is deferred. Containment confirmed by the owner on 2026-10-15. (DESIGN §5.5; docs/architecture.md, Tools)

- **Hotkeys go through one dispatcher** with a fixed order (text fields and handled events ignored, then the focused viewport's tool, then the global table), and Space toggles Play/Pause on release only if no Space + drag pan happened; on a focused button Space keeps its native meaning. Reason: Space is both a pan modifier and the Play/Pause hotkey. (DESIGN §5.9; docs/architecture.md, Actions and hotkeys)
- **RagImporter is the `lib/` folder,** with `lib/ragimporter.js` as the only public entry. Hosts copy `lib/`; `demo/` imports only the entry; the editor may import internal `lib/` modules. Reason: schema, emitter, validation, serializer and evaluator must be shared, pure and testable, which one file would not allow at a reasonable size. (DESIGN §7, §8, §9)
- **Conformance with `docs/architecture.md` is checked:** automated by #66, as an item of the PR template, and by architect review of any PR that adds or changes a module. (docs/architecture.md, Conformance)
- **The header is a full-width toolbar with per-group alignment.** File, History and Playback sit on the left in that order, and Workspace (Window, Settings) sits at the right end. It has a single Tab stop with a roving tabindex. Unavailable actions use `aria-disabled` and stay focusable, and tooltips only show §5.9 hotkeys. Reason: "top center" did not say how the groups line up, and the shell built for #7 follows the usual editor layout, with document and playback actions near the tools and workspace settings out of the way. (DESIGN §5.3)
- **The viewport host stays `role="group"` until the viewport handles keys itself, then becomes `role="application"`.** Reason: screen readers use single-key hotkeys (V, B, M, F, Space…) for browse-mode navigation unless the focused region is an application, and an application role is not justified before there are keys to pass through. Its scope is limited to the viewport host. (DESIGN §5.4)
- **liquidfun.js is the doebi/liquidfun.js v1.1.0 Emscripten (asm.js) build**, reached through its `Box2D` namespace global with WebIDL accessors; RagImporter never assumes global `b2*` names. `RagImporter.configure` accepts `{ Box2D }` as well as `{ PIXI }`, both optional. It is the build the project owner uses, is self-contained and matches the reference demo byte for byte; injecting the namespace mirrors the PIXI handling and lets tests and module-based hosts supply it without a global. (DESIGN §7, §12)
- **PIXI.js is pinned to 8.21.0** after verifying `Assets`, `sortableChildren`/`zIndex` and `eventMode` + `pointermove`. (DESIGN §7, §12)
- **RagImporter targets LiquidFun + PIXI.js directly**, with no engine/renderer adapter layer. The project only targets this stack; an adapter layer can be added later if needed. (DESIGN §7)
- **Procedural joint control lives in RagImporter**; authoring (`aimAxis`) and preview live in the editor. Targets come from runtime data the editor cannot key. (DESIGN §4.8)
- **Shapes carry sprites** (offset, angle, scale, z), and the timeline can swap them through a discrete `sprite` channel. (DESIGN §2.3, §4.2)
- **The root is a world object** that parents everything and owns the global `strength`/`gain`/`damping` channels. These are 0–1 multipliers, never overrides, so a "dead" clip needs a single track. (DESIGN §2.1)
- **Springs are emulated with joint motors** (PD over motor speed, torque scaled by strength), because LiquidFun revolute joints have no spring. (DESIGN §3)
- **Layers:** the higher index wins; override by default, additive optional; no masks, since a clip only affects the tracks it has. (DESIGN §4.4)
- **Transitions** use per-clip `fadeIn`/`fadeOut`; a transition matrix is backlog. (DESIGN §4.1)
- **Grouping replaces FixedJoint**: a body can have several fixtures. (DESIGN §2.2)
- **The editor's Simulate mode uses RagImporter**, so preview equals production. (DESIGN §3, §5.1)
