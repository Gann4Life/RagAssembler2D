# Tools: registry and input routing

**`new ToolRegistry(core, tools)`**, `core` = `{ model, history, selection, modes, settings, camera }`, `tools` = `Tool[]` (an id twice throws).

- **Queries:** `list()` (registered tools in `TOOL_SPECS` order), `get(id) → Tool | null`, `has(id)`, `active → Tool | null`, `canActivate(id)` (registered and `modes.can(capability)`).
- **Start:** `select` is active when registered, else no tool (`active === null`, which only registries built without Select in tests reach; the toolbar then shows no pressed button). No `tool` event at construction. `createEditor` registers Select from #13 on, so the editor starts with Select active and `js/main.js`'s start refresh presses its button and puts the roving stop on it, with no toolbar change.
- **`activate(id) → boolean`:** `false`, with no change, when `!canActivate(id)`. `true` with no change when `id` is already active. Otherwise `cancel()`, `deactivate()` the old tool, `activate(ctx)` the new one, apply its cursor, invalidate the overlay, emit `tool` `{ id, previous }` (`previous` is an id or `null`).
- **`pointer(input: ToolPointerInput)`:** fills `world = camera.screenToWorld(screen)` and `local = toLocal(world)`; ignored with no active tool.
  - `down`, button 0: ignored while a press is open and not cancelled. A cancelled press ends here (below). Then ignored while `history.inGesture` (a gesture owned elsewhere); else opens the press, `history.beginGesture()`, `tool.pointerDown(e)`.
  - `down`/`up`, button 2: passed to the tool without a gesture, unless a left press is open, cancelled or not (then ignored).
  - `move`: passed to the tool, hover moves included. While the press is cancelled, moves with the primary button held (`buttons & 1`) are swallowed.
  - `up`, button 0, of the open press: closes the press, `tool.pointerUp(e)`, then `history.endGesture()`. The release of a cancelled press is swallowed.
  - **A cancelled press ends** at its release, at the first `move` without the primary button (that move then reaches the tool), or at the next left `down`, whichever comes first, so a release lost after a cancel (capture already gone) never blocks the next press.
  - **A handler that throws** during a press (`pointerDown`, `pointerMove`, `pointerUp`, `keyDown`) aborts it like Esc: `cancel()` runs (for `pointerUp`, after the press was closed, so `tool.cancel()` and `history.cancelGesture()` revert whatever the release executed and nothing is recorded), then the error is rethrown. Outside a press (hover moves, right button, keys) errors are rethrown without a cancel.
- **`key(event) → boolean`:** `false` with no active tool or for `Escape` (and the legacy `Esc` key value; Esc always reaches the `escape` action); else `tool.keyDown` of the converted `ToolKeyEvent`, `true` only when it returns `true`. Tools consume only keys their issue documents, never tool hotkeys or §5.9 keys.
- **`cancel() → boolean`:** marks an open press as cancelled (its remaining events are swallowed), calls `tool.cancel()`, then `history.cancelGesture()`, invalidates the overlay, and returns whether either aborted something.
- **Listeners** (subscribed in the constructor; the registry is built before any other `mode` subscriber, [Editor composition](editor-composition.md#editor-composition)): `mode` → `cancel()`, then, when the active tool is no longer allowed, `activate('select')`, or with Select not registered, `deactivate()` and `active = null` (emits `tool`); `history` → when a press is open but the state reports no gesture (Undo closed it, or a reset dropped it), mark the press cancelled and call `tool.cancel()`; model `reset` → `cancel()`.
- **`bindView(view: ToolView) → () => void`:** connects the viewport; until bound and after unbinding, `hitTest` returns `[]` and the other view calls do nothing. The registry calls `view.setCursor` with `override ?? tool.cursor`, or `'default'` with no active tool, on binding, on activation (which clears the override) and on `ctx.setCursor`. `js/viewport.js` implements it by setting the `--tool-cursor` custom property on the host, which `css/editor.css` uses as `cursor: var(--tool-cursor, default)`; the inline `grab`/`grabbing` cursor that `js/viewport/input.js` sets while navigating overrides it, so navigation wins without the two modules sharing state.
- **`drawOverlay(g)`:** `g.clear()`, then the active tool's `drawOverlay(g)`. The viewport calls it at most once per frame, after `invalidateOverlay()`, a `camera` event or a `tool` event.
- **`handleAt(screen) → string | null`** and **`readout() → { text, screen } | null`** (#128): the active tool's, or `null` with no active tool or while no view is bound. The viewport uses `handleAt` to suppress object hover over tool handles and draws `readout` as text in the tool overlay ([Tools](tools.md#tools), Select transform).
- `on/off('tool')`.

**Input routing** (`js/viewport/input.js`, UI). Navigation (pan, zoom) is handled first and never reaches tools; `F` and `Home` are the `frame-selection` and `frame-all` actions.
- Left presses (without Space held) and right presses on the host become `tools.pointer({ type: 'down', … })`; a left press captures the pointer. Moves over the host, or captured, become `move`; releases become `up`. `clicks` is 2 for a press within `DOUBLE_CLICK_TIME` and `DRAG_THRESHOLD` of the previous click's press, else 1. The host's `contextmenu` is always prevented.
- Buttons pressed or released while another is held arrive as `pointermove` with `button ≥ 0` and are handled as presses and releases. A middle press during a left press starts a pan on the same pointer, keeping the capture.
- `pointercancel`, `lostpointercapture` and window `blur` during a left press call `tools.cancel()`. Known limitation ([`DESIGN.md` §5.4, §12](../design/12-open-items.md#12-open-items--to-verify)): when Chromium was driven through the DevTools Protocol, a middle press during a left drag released the capture, so the drag was cancelled instead of panning; to be verified with a physical mouse.
- After a pan or zoom step during a left press, and on a `keydown`/`keyup` of Shift, Control, Alt or Meta on the host while a press is open or the pointer is over the host, the last pointer position is re-sent as a `move` with the current modifiers. The Alt `keyup` is prevented so the browser menu bar does not take focus ([`DESIGN.md` §12](../design/12-open-items.md#12-open-items--to-verify)).
- Hover: idle moves (no button, no navigation) call `onHover(screen)`, at most once per animation frame (`requestAnimationFrame`); leaving the host, any press, navigation and window `blur` call `onHover(null)`.

**Selection display and hit testing** are not tools: hover, selection and invalid outlines come from `js/viewport/gizmos.js`; what a click or a box selects is the job of the Select and Select Box tools (Select and Select Box, above), using `ctx.hitTest` and `ctx.boxTest`.
