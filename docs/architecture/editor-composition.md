# Editor composition

`js/editor.js`: `createEditor({ settings } = {}) → Editor` (frozen) builds, in this order, `model = new Model()`, `history = new History(model)`, `selection = new Selection(model)`, `modes = new Modes(model)`, `camera = new Camera()`, `tools = new ToolRegistry({ model, history, selection, modes, settings, camera }, TOOLS.map((createTool) => createTool()))` and `actions = new ActionRegistry()`, and adds `settings`. `TOOLS` is the module's private list of built tool factories (`circleTool`, `boxTool`); it takes no `tools` option (tests use `ToolRegistry` directly).

- **Cancellation first:** the tool registry subscribes to `mode` in its constructor, before anything else subscribes to `modes` (`settings` and `camera` subscribe to nothing), so its listener, which calls `tools.cancel()` ([Tools](tools.md#tools)), is the first one. `tools.cancel()` cancels the tool and any open gesture, including one the registry did not open (an inspector scrub); the editor has no cancellation listener of its own. Emitters run listeners in subscription order, so other `mode` listeners (Simulate start, #54) never see a half-done gesture.
- **Settings and camera:** `settings` is the given `Settings`, or `Settings.restore(undefined).settings` when omitted, so tests need no storage; anything else given as `settings` throws `TypeError` before anything is built, so a wrong restore result fails at boot instead of at the first `get`. Neither listens to `modes`, and neither is undoable. `js/editor.js` registers no viewport or settings action: `settings`, `frame-selection` and `frame-all` need the DOM or the viewport and are registered by `js/main.js` ([Viewport camera, grid and snapping](viewport-camera-grid-snapping.md#viewport-camera-grid-and-snapping)).
- **Core actions** registered here: `undo` and `redo` (`isEnabled`: `modes.can('history')` and `history.canUndo`/`canRedo`; `reason`: the mode reason when the policy refuses, else `null`; `repeatable`), `escape` (`if (!tools.cancel()) selection.clear()`), and one `tool:<id>` action per registered tool: `run` → `tools.activate(id)`, `isEnabled` → `tools.canActivate(id)`, `reason` → the mode reason for the tool's `capability`. They never execute commands, so they stay enabled during a gesture, and switching tools cancels it. Tools in `TOOL_SPECS` that are not registered have no action, so their hotkey and button report "not available yet". `undo` is unchanged: when it cancels a tool's gesture, the registry sees the gesture close and cancels the tool ([Tools](tools.md#tools)). Actions whose feature is not built are not registered, so they report `'not available yet'`; `play`, `pause`, `next-frame`, `stop` and `toggle-play` arrive with #54, mode switching UI with the Timeline (#32).
