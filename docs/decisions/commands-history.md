# Decisions: Commands and history

Newest first. See the [index](../decisions.md).

## 2026-10-15
- **Actions that execute commands are disabled while a history gesture is open;** only the gesture owner executes commands inside it. Undo and Esc still cancel the gesture. Reason: a command that removes the open clip inside a gesture makes the mode-change listener call `cancelGesture()` re-entrantly, which throws (recorded as a known limitation; unreachable in #10, where no command removes nodes); and a key pressed mid-drag must not become part of the drag's undo step. Disabling at the action level fixes both without making history defer re-entrant calls. Applies from the first command action after #10 (Delete, #19). (DESIGN §5.9; docs/architecture.md, Commands and undo, Actions and hotkeys)
- **Edge cases of the #10 core are fixed as implemented:** `selection.set([])` clears both lists and keeps focus, `add([])` does nothing; without an open clip the playhead stays 0; removing the open clip in Simulate keeps the playhead until Stop, which returns to Edit at 0; "a gesture with changes" (for `canUndo`, `undoLabel`, `dirty`) means one `endGesture()` would record; `undo()` with an open gesture returns `true` even when it had no changes; a new `History` treats the initial document as saved. Reason: the spec left them open, and each choice matches the nearest existing rule (`clear`, clamping, the Stop rule, `endGesture`, `cancelGesture`, the `new` reset). (docs/architecture.md, Commands and undo, Selection, Modes)
- **Gesture coalescing is restricted, and a net no-op gesture leaves no step.** A `set` merges into an earlier `set` on the same uid and path only when no op between them sets an overlapping path of that uid (`sprite` vs `sprite.offset`) or adds/removes a subtree containing it; otherwise it is appended. A gesture made only of `set` ops whose `previous` equals their `value` is discarded on end. Undo during a gesture only cancels it; Redo during a gesture does nothing; cancelled and discarded gestures keep the redo stack. Reason: unrestricted coalescing makes redo wrong when a gesture mixes whole-object and field sets on the same node, and an undo step that changes nothing looks broken to the user. (DESIGN §1; docs/architecture.md, Commands and undo)
- **History clears itself on the model's `reset` event instead of exposing `clear()`,** with the saved point at the new document for `new`/`load` and unreachable for `recover`. `dirty` stays true once the saved state can no longer be reached. Reason: callers could not get the order of `reset` and `clear` wrong (cancelling a gesture after a reset would apply ops to stale uids), and a recovered draft is by definition unsaved. (DESIGN §1; docs/architecture.md, Commands and undo)
- **History keeps the completed ops returned by each `tx` call and updates its stacks even when a model listener throws,** then rethrows; history calls made from inside `run` or a `change` listener throw. `execute` returns the value of `run`. Reason: `model.batch` throws after applying when a listener throws, so its return value is lost and history would drift from the model; re-entrant calls would nest batches. Returning `run`'s value lets create commands hand back the new uid without a side channel. (docs/architecture.md, Commands and undo)
- **`setProps` refuses `id` paths and checks no types or ranges; multi-clip renames apply key-follows-name in order.** Reason: ids never change (DESIGN §1); types and ranges are already constrained by the inspector and reported by validation (#25), and drafts may be invalid; sequential application keeps keys of clips renamed together unique. (DESIGN §1, §4.1; docs/architecture.md, Commands and undo; docs/schema.md)

## 2026-10-14
- **A command's transaction is a `model.batch(fn)`.** Inside `fn`, each `tx` call is an `applyOps([op])` that applies immediately; the batch defers emission and emits one `change` (`do`) at the end, or reverts every op and emits nothing if `fn` throws. It returns `{ ops, changes }`; history records the ops and discards the entry when there are no changes. Batches do not nest. Undo, redo and cancel stay single `applyOps` calls. Reason: `run` must read its own writes and views must see one consistent change per command; keeping the revert logic in the model, which already has it for atomic `applyOps`, avoids a second, non-emitting mutation path and unbalanced begin/end calls. (docs/architecture.md, Document model, Commands and undo)
- **`applyOps` returns the completed ops,** with every derived field (`previous`, indexes, move `from`, removed snapshots, assigned uids) filled; these are what history records and inverts. Ops with no effect (a JSON-equal `set`, a `move` to the same slot) produce no change and no event, but are still returned. Reason: callers pass only intent, and inverse data comes from the one place that knows the state. (docs/architecture.md, Document model)
- **Undo uses command objects recorded as primitive operations, not model snapshots.** A command's `run(tx)` mutates the model only through `set`, `add`, `remove` and `move`; the history stores those ops with their inverse data, undo reverts them in reverse order and redo replays them. Reason: each op is also the change notification the views need, so the viewport, hierarchy and inspector update only what changed instead of diffing snapshots or rebuilding; a step costs only what changed, which keeps 200 steps cheap; redo replays the same ops, so ids and session uids stay identical; and inverses are mechanical, so commands never write hand-made `undo` code. (DESIGN §1; docs/architecture.md, Commands and undo)
- **One user operation is one undo step.** A compound command (delete with cascade, group, ungroup, duplicate, create + assign `rootBody`) is one transaction. Continuous edits merge through gestures: everything executed between press and release (or during an inspector scrub) is one entry, with `set` ops on the same path coalesced; Esc, tool switch, mode change or Undo during a gesture reverts it without leaving a step. Reason: time-window or per-command merge keys are fragile, and the gesture boundary is exactly what the user perceives as one action. (DESIGN §1, §5.6)
- **Model changes are batched per transaction and the viewport flushes once per frame.** The model emits one `change` event (list of add/remove/set/move) per commit, undo, redo or cancelled gesture, and `reset` on New/Load/recover; the scene keeps PIXI display objects keyed by uid and only updates dirty entries. Reason: views always see a consistent model after compound commands, and long drags cost one redraw per frame. (docs/architecture.md, Change notifications, View sync)
