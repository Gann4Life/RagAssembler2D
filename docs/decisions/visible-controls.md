# Decisions: Visible controls and feedback

Newest first. See the [index](../decisions.md).

## 2026-10-25 (every clip simulation starts in the clip's pose, owner report)
- **The clip simulation and Simulate from Animate spawn every clip, looping or not, in the clip's own pose at time 0 (`pose` spawn option); a clip without keys starts at rest.** Owner: with `loop` off, the first keyframe could not be set because frame 0 always showed the rest pose. Reverses the 2026-10-23 rule "non-looping clips start from the rest pose". Editor preview only: runtime `play(key)` still blends from the current pose and never respawns; posed spawn stays the explicit `spawn({ pose })` option. (DESIGN §5.1)

## 2026-10-24 (Pose drag influence falls off with joint distance, owner design #194)
- **In Animate, Pose holds every joint and body with a strength that grows tenfold per joint hop from the grabbed body.** Joint motors hold their press angle with a torque cap of 0.1 × 10^(d − 1) of the torque the pull can exert about them; other bodies get a ground hold of 0.1 × 10^(h − 3) of the pull's force; the pull runs at 15 Hz with 64 velocity iterations. Owner: dragging the shin should move the shin, thigh and foot, maybe the pelvis slightly, nothing beyond, on any rig. Cause: free hinges and a free `rootBody` in zero gravity let the pull drag the whole ragdoll, so every joint was keyed. Measured (drag 0.36 m on `human_full`, 0.18 m on the robot; angle change by distance `d`, before → after): shin `d=0` 74° → 13°, `d=1` 8° → 15°, `d=2` 12° → 0.00°, `d≥3` up to 2.7° → 0.00°; robot shin `d=1..4` 74°, 73°, 12°, 39° → 12°, 0.00°, 0.00°, 0.00°; forearm drags alike; the grabbed point ends within 1–3 cm of the pointer when reachable. Rejected: friction holds (no return to the press angle) let far joints creep 0.3–0.7°; ground holds one hop closer made the foot counter-rotate 27° instead of following the shin; 8 iterations let far holds fight the near ones (a wrist 3 hops away bent 4.6° on a root drag). Trade-off: a target the near joints cannot reach leaves the grabbed point short rather than moving the pelvis; `rootBody` is held by distance like any body, not pinned. Edit-mode Pose keeps free hinges. Supersedes the §5.5 sentence "dragging a limb can pull the whole rig along". (DESIGN §5.5)

## 2026-10-24 (Pose keys the released angle, owner report)
- **Pose keys each changed joint at its released angle, clamped to enabled limits; root `bodyAngle` at its released value.** The change threshold of the entry below stays, so untouched joints keep their keys. Cause: with evaluated + change, a display lagging the keys added the lag to the key (evaluated −16.6°, press −1.5°, release −59.2° gave −74.4° on a ±60° hip of the owner's robot), and every correction from the lagging display pushed further (keys of −2.68 rad on ±1.57 rad joints). The released angle is what the user saw and the test enforces the limits. Supersedes the key value of the entry below. (DESIGN §5.5)

## 2026-10-23 (Pose keys are relative, owner report #192)
- **Pose keys the change since the press, added to the evaluated value.** A joint (or root `bodyAngle`) is keyed only when its measured value changed by more than 0.1° between the press and the release, and the key is the evaluated value at the playhead + that change. Owner: "each time I make a correction, the pose doesn't stay exactly where I wanted it; over time it offsets more and more." Cause: the displayed start is the clip simulation, which lags the keys (motor tracking, gravity), and absolute keying baked that lag into every joint on every release, so it compounded. Measured on the humanoid test rig (playhead 0.5 s, right hand dragged ±12 px, 8 releases): untouched-joint key drift went from 22° after one release and up to 48° (root `bodyAngle` key up to 11.5°, 15 tracks keyed) to legs and root exactly unchanged, with at most 2.6° on the chest, head and other arm, which the drag itself turns through the free hinges and damping, bounded rather than growing. Trade-off: the keys no longer record the pose as seen; after the handover the figure still shows what physics does with the keys. Supersedes "unchanged formulas … 0.1° threshold vs the evaluated value" in the entry "Pose starts from the displayed bodies" below. No format change. (DESIGN §5.5)

## 2026-10-23 (clip simulation start and looping clips, owner decision)
- **Non-looping clips spawn in the rest pose; looping clips spawn in the clip's pose at time 0 and run continuously through cycles.** Owner: "Always start from the rest pose when loop=false; if loop=true the simulation must be continuous; option C also seems coherent." The run of a looping clip keeps the bodies' state across wraps; the playhead carries a cycle (1 on opening a clip); the run computes cycles in order up to the later of cycle 2 and the one after the playhead's, never past a cycle limit of 8. Play wraps into the next cycle and pauses at the end of the limit with "Clip simulation: cycle limit 8 reached" (Play then restarts from cycle 1); Next frame wraps likewise; Stop restores the cycle too; scrub moves within the playhead cycle; ghosts and the progress bar show the playhead cycle; a Timeline cycle control `‹ cycle c ›` (looping clips only) shows it and moves it like a scrub. Simulate from Animate spawns the same way, with no limit. Reason: a deterministic, bounded, visible model; cycle 2 is always there because it shows what the wrap does, and a fixed limit beats a convergence test that may never trigger for a rig that falls over. Supersedes the trade-off of the earlier entry "Clip simulation: one deterministic … run" (a looping clip run once, its wrap showing time 0's state) and resolves the §12 "Simulation at time 0" item. Trade-off: posing at time 0 of a non-looping clip keys the pose but the frame at 0 stays the rest spawn (owner-accepted). (DESIGN §5, §5.1, §5.8, §12)

## 2026-10-23 (Pose on the simulated pose, owner feedback after testing)
- **The Animate main figure is always the clip simulation at the playhead, with every tool (owner rule).** Playing, paused or scrubbed; choosing Pose never changes what is displayed. The FK pose is shown only when the clip simulation is not available (validation errors), and the rest pose only as the run's own spawn. Reason: the owner animates from what he sees simulated; turning the view to the FK pose on choosing Pose, and the jump back after Stop, lost the frame he wanted to correct. Supersedes this file's earlier same-day entry "Animate view by tool: Pose shows the FK pose …" and the "FK preview while Pose is active" rule. (DESIGN §5.1, §5.4, §5.8)
- **Pose starts from the displayed bodies; a press while playing pauses and grabs in the same press.** The test starts from the displayed step (or held or blended pose) at rest, `rootBody`'s center of mass and angle held as before; on a press while playing the playhead stays at the displayed step's time. A click (no drag) writes nothing, so a Pose click while playing only pauses. Keys: unchanged formulas (`GetJointAngle()`, `bodyAngle` = angle − rest angle, 0.1° threshold vs the evaluated value, autokey rules), now usually keying every joint physics moved off its evaluated value. Reason: "correct it the moment I see it"; pausing first and grabbing on a second press was one press too many. Trade-offs: denser keys; keys land on step times, not on the Timeline snap. Supersedes "Pose starts from the FK pose; the posed preview is removed" and "a Pose press while playing only pauses"; restores the starting rule of the earlier "A Pose press starts from the displayed pose exactly" entry, with the display after release redefined below. The §12 "Pose from a physics pose" verification is back. No format change. (DESIGN §5.1, §5.5, §12)
- **Posed hold and handover instead of an FK display after the release.** The released bodies stay on screen until a run started after the last committed change reaches the playhead, then the figure blends into the run in 150 ms (position and continuous angle, smoothstep); the same blend covers every source change of the main figure that the user did not cause by moving the playhead (previous run or latest reached step to the current run). Scrub, Next frame, Stop, another clip and leaving Animate end the hold at once; Play during the hold waits at the playhead until the handover, then plays on the recomputed run. Pause never drops the run. Reason: the release must not jump, and the run after the edit is the truth the owner wants to see next; the blend is display only. Trade-off: after the blend the figure shows what physics does with the new keys, which can differ from the released pose. (DESIGN §5.1, §5.5, §5.8)
- **Dropped:** a neutral gray ghost at the playhead (the main figure is already the simulation). Ghosts stay as specified: the pose at a time at each key time, green ahead and red behind, shapes only; the hold and the handover never apply to them. (DESIGN §5.1)
- **Pending owner items resolved as post-MVP options:** Stop while paused and Play from start are not needed for the loop (Pause keeps the simulation, Pose works paused); recorded in §12 with a snap-on-pause option. New owner decision recorded in §12: the run spawns the rest pose at time 0, so posing at or near 0 blends back toward rest; options and recommendation listed there. (DESIGN §12)

## 2026-10-23 (animating loop, owner model)
- **Animating happens in Animate alone; Play, Pause, Stop and scrub never change the mode or the tool (owner rule).** In Animate, Play moves the playhead in real time and stays in Animate; Pause, Next frame and Stop work there too (Stop returns the playhead to where Play started); scrubbing is always allowed and pauses playback. Simulate stays only as the live physics test (rest pose from Edit, the open clip from 0 from Animate). It is entered by the mode switch's *Simulate* segment, which starts that live run itself (it no longer runs Play, and Space is no longer its hotkey), or by Play in Edit mode; Play in Animate never enters it. Stop in Simulate, or the *Edit* or *Animate* segment, ends it first and restores the mode before it. So the modes change through the mode switch, Play in Edit, Stop in Simulate, the clip selector and New clip. Reason: the owner animates by watching, fixing and playing again, with no interruptions; procedural preview, clip triggers and contacts still need a live run, so Simulate is kept but taken out of the loop. Supersedes in this file's earlier 2026-10-23 entries: scrub disabled in Simulate with Animate as the continuation; "Simulate runs Play"; Animate continuing from the time the simulation reached; and "Play / Stop" as mode controls in every mode. (DESIGN §5, §5.1, §5.3, §5.8, §5.9, §12)
- **Clip simulation: one deterministic, background-computed run of the open clip, stored per step, replaces the physics scrub preview.** Run from 0 to `length` at the fixed 60 Hz step within the per-frame budget, the open clip alone; restarted 250 ms after the last committed change, showing the previous run until the new one reaches a time; dropped on another clip or leaving Animate. Scrub, Play and ghosts all read it. Reason: going back no longer re-simulates, play and scrub always agree, and the ghosts need the same poses; storing transforms is cheap (bodies × steps × 3 numbers). Trade-off: a looping clip is run once, so playback after the wrap shows time 0's state, not the momentum of the previous loop. Cost to measure (§12). (DESIGN §5.1, §5.8, §12)
- **Animate view by tool: Pose shows the FK pose, every other tool the clip simulation; while playing, the simulation with every tool.** Choosing Pose is the user's action that turns the view to the keyed pose. A Pose press while playing only pauses. Replaces "after a scrub the physics scrub preview" and the displayed-pose order of the earlier entry. Reason: the owner poses on the keyed pose and watches physics; playing with Pose active must still show physics, so the transport wins while playing. (DESIGN §5.1, §5.4, §5.5, §5.8)
- **Pose starts from the FK pose; the posed preview is removed.** Supersedes "A Pose press starts from the displayed pose exactly; a posed preview holds the released bodies". With the FK pose as the start and `rootBody`'s center of mass held at its FK place, the FK pose of the written keys matches the release within 0.1° per joint, so nothing jumps without a posed preview. Measured values, key rule and threshold are unchanged; the §12 "Pose from a physics pose" verification is dropped. No format change. (DESIGN §5.1, §5.5, §12)
- **Ghosts (onion skins) in the MVP (#184):** the clip simulation drawn at every key time of the open clip (events excluded, none at the playhead's step), green after the playhead and red before, shapes only (12 % fill, 1 px outline at 50 %, the grid axis colors so they never read as validation errors), above the grid and below the figure, in every display mode, never hit. They update with the run after a committed edit, not during a drag. Reason: the owner fixes poses against what physics does at the other keys; key times are the moments he authored. Post-MVP: live update during drag, options (count, opacity, on/off), preview stack ghosts (§12). (DESIGN §5.1, §5.4, §12)
- **Disabled reasons for the new transport states:** Pause and Stop "not playing" in Animate, Next frame "at the end of the clip" for a non-looping clip at `length`, Play in Edit mode and the mode switch's *Simulate* segment "fix the errors in Problems" with validation errors; Play is allowed in Simulate (resume), matching the existing toggle. "Delete clip, scrub: open a clip" becomes Delete clip only, since scrubbing is always allowed in Animate. (DESIGN §5, §5.1)
- **UI review fixes (same day):**
  - Pose with autokey off reports "Pose: autokey is off, no keys written" when the release would have keyed something. Reason: a release that silently writes nothing reads as a bug.
  - Clip simulation progress: a 3 px bar at the bottom of the ruler, solid to where the current run reached, the previous run's range hatched beyond it. Reason: the user must see why the figure lags after an edit.
  - One "pose at a time" rule for the main figure and the ghosts: current run once reached, else previous run, else the latest step reached (main figure, also while playing) or no ghost.
  - With validation errors Animate shows and plays the FK pose, and the status line says "Clip simulation: fix the errors in Problems" on entering Animate and on the first error.
  - Next frame on a looping clip at `length` wraps to 0 plus one step.
  - Key selected keys the evaluated (FK) value, never the simulation shown.
  - Pose while playing shows the default cursor and no hover, since a press only pauses.
  - A Play / Pause button first in the Timeline bar (Godot-like), so §5.9's "Timeline Play" control exists and the loop needs no trip to the header.
  - §5.9 lists Ctrl+C, Ctrl+V and Del for keys "while keys hold the selection focus", taking precedence over the Hierarchy Delete.

  (DESIGN §5, §5.1, §5.5, §5.8, §5.9)
- **Sliding recorded, not decided:** owner-reported sliding goes to §12 with today's values (ground 0.8, shape default 0.6). (DESIGN §12)

## 2026-10-23
- **No action is hotkey-only (owner rule).** Every action, tool, mode and toggle has a visible control; hotkeys are accelerators shown in that control's tooltip (menu items also show them right-aligned). §5.9 becomes one row per hotkey with its visible control, and Esc is the only exception as the universal cancel key. Homes given now: a header **Rig** menu (Rename, Duplicate, Delete; Group, Ungroup, Split; Set as root body, Fit motor torque; Sprite edit checkbox), a header **View** menu (Frame selection, Frame all), Settings › Gizmo › Pivot (Z), Timeline Copy / Paste / Delete keys buttons; Key selected keeps its §5.8 Timeline button. Reason: the owner could not find Shift+M, Shift+R or the mode; one menu gives the six hotkey-only rig actions a home without crowding the 300 px Hierarchy toolbar with cryptic icons, and a menu lists the hotkeys, which teaches them. Trade-off: one more click than a toolbar button; the inspector (#20) adds per-object entries later. Supersedes the 2026-10-23 hierarchy entry's "no button, the inspector gives the discoverable entries". (DESIGN §5, §5.3, §5.5, §5.6, §5.8, §5.9)
- **The user decides tools and modes (owner rule).** No automatic tool switch: a mode change never changes the active tool; a tool the new mode disables stays active, pressed and dimmed, with the mode reason, and a viewport press with it only shows the reason in the status line. Modes change only through the header mode switch, Play / Stop, the clip selector and New clip; New / Load and the removal of the open clip still return to Edit as consequences of explicit actions, the latter with a status message. Replaces "a mode change that disables the active tool activates Select" (§5.1, §5.5). Reason: silent swaps left the owner unable to pose after Pause (Simulate had switched Pose to Select); a visible disabled state with a reason is predictable. (DESIGN §5, §5.1, §5.5)
- **Header mode switch: segmented Edit | Animate | Simulate between Rig and Playback.** Always visible, independent of the Timeline. Animate opens the last opened clip of the session, else the first clip, else creates one ("New clip", one undo step, status "Created clip *name*"); the tooltip says which. Simulate runs Play. From Simulate, Edit stops then enters Edit; Animate enters Animate at the time the simulation reached and keeps the simulation as the physics scrub preview (the view does not change). Reason: the mode was only implied by the clip selector, hidden while the Timeline is folded (§12 open item, now resolved); creating a clip on Animate avoids a dead end with no clips. (DESIGN §5.1, §5.3, §5.8, §12)
- **Scrubbing in Simulate is disabled ("only in Animate mode"); Animate in the mode switch replaces the old scrub-returns-to-Animate path.** Reason: the old rule changed the mode implicitly; the new path keeps the same continuation (simulation kept as the scrub simulation) behind an explicit control. Alternative left to the owner (§12): seek inside paused Simulate without leaving it. (DESIGN §5.1, §5.8, §12)
- **Pose is the animation tool; Select only selects in Animate and Simulate (owner rule).** The Animate rotation ring of #125 (parent joint `angle` and root `bodyAngle` keys) is removed: no gizmo, no handles, every drag draws a selection box. Reason: one way to pose, which is the owner's workflow; Pose already covers joint angles and `rootBody` turns. (DESIGN §5.1, §5.4, §5.5, §5.8)
- **A Pose press starts from the displayed pose exactly (owner decision); a posed preview holds the released bodies.** In Animate the test starts from the posed preview, else the physics scrub preview, else the FK pose, with zero velocities, `rootBody`'s center of mass held where it was at the press. Keys (autokey on) are measured from the released bodies: `GetJointAngle()` per joint and `bodyAngle` = `rootBody` angle − rest angle, keyed where they differ from the evaluated value by more than 0.1°, so a pose started from physics keys every joint physics moved. After the release the viewport shows the released bodies until the playhead moves, another clip opens, the mode changes or another document change happens. No format change. Reason: no jump on press or release; the formulas reduce to the previous ones when the start is the FK pose. Accepted limitation: when the posed preview is dropped, FK puts `rootBody`'s center of mass back at rest (no root position channel, §13). Verification in §12. (DESIGN §5.1, §5.4, §5.5, §12)
- **Every disabled control gives a reason, state reasons included; activating it shows "*Label*: *reason*" in a new status line.** Mode reasons now name where the action works ("only in Edit mode", "only in Edit and Animate modes") instead of where it does not. A §5 table lists the state reasons (Undo, Redo, Play, Pause, Delete, Duplicate, Rename, Group, Ungroup, Split, Set as root body, Sprite edit, Delete clip, scrub). No reason during a drag, scrub or confirmation. Replaces §5.3's "nothing when only the state disables it" and the Delete and Group exceptions it needed. Reason: a silent no-op on a hotkey or click is the "ghost method" the owner described; naming the allowed mode is actionable now that the mode switch is visible. Trade-off: every tooltip and reason test changes wording. (DESIGN §5, §5.3, §5.5, §5.6, §5.9)
- **Status line: one polite live-region line at the bottom center of the Viewport panel, 4 s, replaced by the next message.** Used by disabled activations, Fit motor torque ("Fit motor torque: *N* of *M* joints changed, balance *B* N·m, …", also when nothing changed), Set as root body ("Root body: *name*, bodyAngle keys converted in *K* clips"), clip creation from the mode switch and removal of the open clip. Not modal: the message dialog stays for load and save errors. Reason: results that change values the user cannot see (torques, keys in other clips) need confirmation without interrupting. Module boundary: core actions report through a new `createEditor` option, a `status(text)` callback (no-op default, like `notify`), rendered by a new UI module; core stays DOM-free and the wording is tested under Node. (DESIGN §5, §5.6)
- **The `rootBody` row shows a "root body" badge** (loop-badge style, in the accessible name), which moves on Set as root body. Reason: the root body was only implied by the tree order. (DESIGN §5.6)
