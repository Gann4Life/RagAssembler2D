# Decisions: Visible controls and feedback

Newest first. See the [index](../decisions.md).

## 2026-10-23
- **No action is hotkey-only (owner rule).** Every action, tool, mode and toggle has a visible control; hotkeys are accelerators shown in that control's tooltip (menu items also show them right-aligned). §5.9 becomes one row per hotkey with its visible control, and Esc is the only exception as the universal cancel key. Homes given now: a header **Rig** menu (Rename, Duplicate, Delete; Group, Ungroup, Split; Set as root body, Fit motor torque; Sprite edit checkbox), a header **View** menu (Frame selection, Frame all), Settings › Gizmo › Pivot (Z), Timeline Copy / Paste / Delete keys buttons; Key selected keeps its §5.8 Timeline button. Reason: the owner could not find Shift+M, Shift+R or the mode; one menu gives the six hotkey-only rig actions a home without crowding the 300 px Hierarchy toolbar with cryptic icons, and a menu lists the hotkeys, which teaches them. Trade-off: one more click than a toolbar button; the inspector (#20) adds per-object entries later. Supersedes the 2026-10-23 hierarchy entry's "no button, the inspector gives the discoverable entries". (DESIGN §5, §5.3, §5.5, §5.6, §5.8, §5.9)
- **The user decides tools and modes (owner rule).** No automatic tool switch: a mode change never changes the active tool; a tool the new mode disables stays active, pressed and dimmed, with the mode reason, and a viewport press with it only shows the reason in the status line. Modes change only through the header mode switch, Play / Stop, the clip selector and New clip; New / Load and the removal of the open clip still return to Edit as consequences of explicit actions, the latter with a status message. Replaces "a mode change that disables the active tool activates Select" (§5.1, §5.5). Reason: silent swaps left the owner unable to pose after Pause (Simulate had switched Pose to Select); a visible disabled state with a reason is predictable. (DESIGN §5, §5.1, §5.5)
- **Header mode switch: segmented Edit | Animate | Simulate between Rig and Playback.** Always visible, independent of the Timeline. Animate opens the last opened clip of the session, else the first clip, else creates one ("New clip", one undo step, status "Created clip *name*"); the tooltip says which. Simulate runs Play. From Simulate, Edit stops then enters Edit; Animate enters Animate at the time the simulation reached and keeps the simulation as the physics scrub preview (the view does not change). Reason: the mode was only implied by the clip selector, hidden while the Timeline is folded (§12 open item, now resolved); creating a clip on Animate avoids a dead end with no clips. (DESIGN §5.1, §5.3, §5.8, §12)
- **Scrubbing in Simulate is disabled ("only in Animate mode"); Animate in the mode switch replaces the old scrub-returns-to-Animate path.** Reason: the old rule changed the mode implicitly; the new path keeps the same continuation (simulation kept as the scrub simulation) behind an explicit control. Alternative left to the owner (§12): seek inside paused Simulate without leaving it. (DESIGN §5.1, §5.8, §12)
- **Pose is the animation tool; Select only selects in Animate and Simulate (owner rule).** The Animate rotation ring of #125 (parent joint `angle` and root `bodyAngle` keys) is removed: no gizmo, no handles, every drag draws a selection box. Reason: one way to pose, which is the owner's workflow; Pose already covers joint angles and `rootBody` turns. (DESIGN §5.1, §5.4, §5.5, §5.8)
- **A Pose press starts from the displayed pose exactly (owner decision); a posed preview holds the released bodies.** In Animate the test starts from the posed preview, else the physics scrub preview, else the FK pose, with zero velocities, `rootBody`'s center of mass held where it was at the press. Keys (autokey on) are measured from the released bodies: `GetJointAngle()` per joint and `bodyAngle` = `rootBody` angle − rest angle, keyed where they differ from the evaluated value by more than 0.1°, so a pose started from physics keys every joint physics moved. After the release the viewport shows the released bodies until the playhead moves, another clip opens, the mode changes or another document change happens. No format change. Reason: no jump on press or release; the formulas reduce to the previous ones when the start is the FK pose. Accepted limitation: when the posed preview is dropped, FK puts `rootBody`'s center of mass back at rest (no root position channel, §13). Verification in §12. (DESIGN §5.1, §5.4, §5.5, §12)
- **Every disabled control gives a reason, state reasons included; activating it shows "*Label*: *reason*" in a new status line.** Mode reasons now name where the action works ("only in Edit mode", "only in Edit and Animate modes") instead of where it does not. A §5 table lists the state reasons (Undo, Redo, Play, Pause, Delete, Duplicate, Rename, Group, Ungroup, Split, Set as root body, Sprite edit, Delete clip, scrub). No reason during a drag, scrub or confirmation. Replaces §5.3's "nothing when only the state disables it" and the Delete and Group exceptions it needed. Reason: a silent no-op on a hotkey or click is the "ghost method" the owner described; naming the allowed mode is actionable now that the mode switch is visible. Trade-off: every tooltip and reason test changes wording. (DESIGN §5, §5.3, §5.5, §5.6, §5.9)
- **Status line: one polite live-region line at the bottom center of the Viewport panel, 4 s, replaced by the next message.** Used by disabled activations, Fit motor torque ("Fit motor torque: *N* of *M* joints changed, balance *B* N·m, …", also when nothing changed), Set as root body ("Root body: *name*, bodyAngle keys converted in *K* clips"), clip creation from the mode switch and removal of the open clip. Not modal: the message dialog stays for load and save errors. Reason: results that change values the user cannot see (torques, keys in other clips) need confirmation without interrupting. Module boundary: core actions report through a new `createEditor` option, a `status(text)` callback (no-op default, like `notify`), rendered by a new UI module; core stays DOM-free and the wording is tested under Node. (DESIGN §5, §5.6)
- **The `rootBody` row shows a "root body" badge** (loop-badge style, in the accessible name), which moves on Set as root body. Reason: the root body was only implied by the tree order. (DESIGN §5.6)
