# Decisions: Runtime and format

Newest first. See the [index](../decisions.md).

## 2026-10-25 (spec reconciled with the code of the animation demo branch)
- **The balance controller applies a rigid wrench over every body connected to `rootBody` with mass, not a torque on `rootBody` alone.** Inertia and angular velocity are those of the whole set about its common center of mass; each body gets `I_b · α` and the force `m_b · α · perp(r_b)` (forces sum to zero), so joints carry no load from it. `parse` stores `m_b` and `I_b` per body of the set (from `bodyMassData`), replacing `I_root`, `I_tot` and the `lerp(I_root, I_tot, S)` inertia of the 2026-10-23 entry. Reason: a light `rootBody` spun past its joints, which then fought it (trembling, tipping, abrupt turns). No format change. (DESIGN §3.2, §7.1, §7.2, §12)
- **`STEP_SETTINGS` and `stepWorld(world, instances, dt)` are exported from `lib/ragimporter.js`** as the single source of frame stepping (1/60 s, 8 substeps of 8/3); the editor's Simulate session, clip simulation and timeline player and `demo/` use them, and hosts must. `lib/instance.js` imports `lib/evaluate.js` (`resolveChannels`) and exports the internal `driveMotor` and `driveBalance` for tests. Additive API, `feat`. (DESIGN §3.1, §7, §7.1)
- **`play` and `stop` throw an `Error` naming an unknown clip key; `isPlaying` returns `false` for it.** `play` never respawns or moves bodies: it blends from the current pose through the motors, unlike the editor's clip simulation, which spawns every clip in its pose at time 0. Reason: a typo in a clip key must fail loudly; the editor start rule is a preview convenience, not runtime behavior. (DESIGN §7.1, §5.1)

## 2026-10-25 (seamless loops, #198, owner decision)
- **`loop` means seamless: in a looping clip every track interpolates from its last key to its first across the wrap, as if the first key were repeated at `t_first + length`.** The wrap segment uses the last key's `interp` (every segment uses its left key's), covers both `t ≥ t_last` and `t < t_first`, has span `t_first + length − t_last`, and is absent when keys sit at both `0` and `length` (their values then decide seamless or jump). Single-key tracks stay constant; discrete channels step across the wrap; angles (joint `angle`, root `bodyAngle`) stay linear without wrapping or shortest path, so a continuous spin keys `0` and `length` explicitly. Non-loop clips keep holding their first and last values. Events, the `loop` event and queues are unchanged. The motor and balance look-ahead and the posed spawn sample through the same evaluator, so their targets are continuous across the wrap; Set as root body samples terms with the loop rule in looping clips. Reason: the owner rejected an explicit option ("automatic"); a looping walk keyed only inside the clip jumped at every wrap (to the first value held before the first key), which the clip simulation and the runtime showed as a snap. Rejected: the first key's `interp` for the wrap segment (breaks the left-key rule); shortest-path angles on the wrap (inconsistent with §4.3 and with joint targets); a validation warning for keys at both `0` and `length` with different values (a valid way to author a spin). Trade-off: a behavior change for existing looping clips whose first key is after `0` or last key before `length` (values before the first key and after the last change, sprites included); no format change and no `version` bump, so files load unchanged and play differently; to be noted in `CHANGELOG.md` under Changed. (DESIGN §4.1, §4.3, §3, §5.1, §2.1)

## 2026-10-24 (firm joints, owner report "it all still feels like jelly")
- **Suggested motor torque is the worst static case, and the editor steps 8 substeps of 8 velocity iterations.** Torque = `I_eff · α + 2 · M · g · min(R_A, R_B)`: the whole ragdoll's weight at the shorter side's straightened reach, so any limb can lift the body pressed into the ground and hold it in any orientation. Cause of the jelly: not torque saturation but Box2D's velocity motors not converging through light bodies (a 20 g thigh between heavier pelvis and foot): far below their torque, the motors miss their speed and the PD oscillates with a growing amplitude (55° on the owner's robot at 1 × 16 iterations, also in free fall without contacts or balance). More iterations help slowly (4° at 64), substeps much more (0.6° at 8 × 8), since the PD runs on each substep; Box2D v3 substeps for the same reason. Gains and damping were measured (G 5–20, D 0.2–2) and do not fix it, so they keep their defaults. Without substeps the new torques make light rigs gain energy, so substeps are required, and §7's example loop shows them. Supersedes the load-aware foot rule of the entry "automatic motor torque". Cost: 2–6× the step time (0.35–0.38 ms per 1/60 s for 13–15-body rigs in Node, was 0.06–0.18). No format change. (DESIGN §3.1, §7, §12)

## 2026-10-23 (posed spawn, owner decision)
- **`spawn` gains an additive `pose` option: a clip key (default `null`) that starts the bodies in that clip's pose at time 0.** The pose is the clip alone at weight 1, placed by `fkPose` (`lib/evaluate.js`, so `lib/def.js` gains that lib-internal import); bodies and joints are built at rest as before (rest reference angles kept), then every body is moved with `SetTransform` at zero velocity before spawn returns; `θ₀` stays the rest value, so the balance targets the clip's `bodyAngle` at once; no clip is started and no event fires. Unknown key: `Error` naming it; wrong type: `TypeError`. Reason: the editor's looping clip simulation must start where the loop starts, and the host must be able to get the same start, so preview equals production. Rejected: an editor-only posed start (editor and runtime would differ); a time argument (not needed yet; can be added later without breaking). Non-breaking: no format change, no `version` bump; the RagImporter API change is a `feat`. (DESIGN §7.1, §7.2, §5.1, §12)

## 2026-10-23 (automatic motor torque, owner rule)
- **Motor and balance torque are automatic; Fit motor torque and Shift+M are removed; no format change.** After every command that changes `bodies`, `joints` or `ragdoll.rootBody`, the editor runs `motorTorqueSuggestions` and `balanceTorqueSuggestion` (§3.1, §3.2, whatever their formulas) on the result and writes every `motor.maxTorque` and `balance.maxTorque` that differs, inside the same undo step; `null` suggestions keep their value; gain, damping, maxSpeed and `enabled` are untouched. A status line "Motor torque: *N* joints updated, balance *B* N·m" reports a change (appended to Set as root body's message). Load and draft recovery apply the same update after migration, with a load note, leaving unsaved changes when anything changed; the Load → Save byte-identical guarantee now also requires the torques to be at their suggestions. New warning `W_MOTOR_UNDERPOWERED` (< 0.1 × suggestion) and `W_MOTOR_OVERPOWERED` extended to the balance, both for host-validated files; their message points to opening the file in RagAssembler. Reason: the owner rejected running Shift+M after rig edits ("the software should update it automatically … or warn the user"); every edit changes the sides of other joints and the balance depends on `rootBody`, so only a full recompute per command works for any rig. With no inspector there is no way to set a value by hand, so in the MVP every value is automatic and a menu item would do nothing. Supersedes in this file the earlier same-day entry's "Fit motor torque (Shift+M) applies it" and its rejection of "rewriting values at load" (now visible through the load note and unsaved changes, and needed so files saved before a formula change come back automatic); supersedes in `visible-controls.md` the Rig menu's Fit motor torque item and its status message, and in `hierarchy.md` the Set as root body rule that left the balance unchanged. Trade-off: torques set by hand in a file are replaced on Load. User-set values later: §12 (recommended: an `auto` flag, format version 3, and a "Reset to automatic" control). (DESIGN §2.1, §5.1, §5.3, §5.5, §5.6, §5.7, §5.9, §6.4, §6.5, §12)

## 2026-10-23
- **`rootBody` orientation is animatable through a root `bodyAngle` channel and a balance controller; format version 2 (owner decision).** New root channel `bodyAngle` (rad, `rootBody`'s orientation relative to rest, default 0, angle semantics: linear without wrap, additive adds, negated with `flipX`). Runtime: a velocity-servo "motor to the world frame" on `rootBody` in `update()`, `ω* = clamp(G·wrapToPi(θ₀ + target − angle) − D·ω, ±maxSpeed)`, `torque = clamp(lerp(I_root, I_tot, S)·(ω* − ω)/dt, ±S·maxTorque)`, `ApplyTorque`; `S`, `G`, `D` from root and runtime multipliers, so `dead` releases it. Parameters live in a new required `ragdoll.balance { enabled, maxTorque, gain, damping, maxSpeed }` (defaults true, 80, 10, 0.5, 20; `balanceTorqueSuggestion(doc)` in `lib/motor.js` = `roundUp2(I_tot·α + M_O·g·|C_O − c_root|)`, written by Fit motor torque); per-instance `setBalance(enabled)`. Editor FK rotates `rootBody` about its rest center of mass; the Animate ring on `rootBody` keys `bodyAngle`; Pose in Animate keeps `rootBody`'s center of mass fixed (and its angle, unless it is grabbed) and keys `bodyAngle` above 0.1°. Format: `version` 2, `supportedVersions` `[2]`, migration 1 → 2 adds `balance` with `enabled: true` and the suggested torque (owner change: no shipped game depends on version 1 behavior and the editor has no Inspector yet to turn it on). Reason: joint motors only drive relative angles, so `rootBody` could neither be keyed nor held upright, and Pose keyed only joint angles while the test had turned `rootBody`, so FK showed the rig rotated. A velocity servo reuses the joint-motor parameters and multipliers and needs no new native objects; the `S`-blended inertia avoids deadbeat overshoot when joints are loose; the wrapped error makes revive turn the short way; COM pivot matches how a torque turns a free body. Named `bodyAngle` to avoid confusion with the locked `ragdoll.angle`. Version bump rather than an optional field: every field is required (§6.2), and an old runtime would otherwise fail on `bodyAngle` tracks with `E_TRACK_CHANNEL` instead of a version message. Rejected: root x/y offsets (position comes from legs and contacts; an offset needs an external force and would only serve FK; backlog §13); `b2MotorJoint` to a static body (implicit and more stable, but needs a world-owned ground body and is unverified in the binding; kept as fallback in §12); plain PD torque with N·m/rad gains (new units, no reuse of motor semantics). Trade-offs: it is an external, non-physical torque (standard active-ragdoll trick) and can hold a ragdoll in poses its feet could not support; hosts must re-save v1 files; FK keeps `rootBody`'s COM fixed, so crouches and jumps preview without vertical motion. (DESIGN §3.2, §4.2, §4.4, §5.1, §5.5, §5.6, §5.7, §5.8, §6.1–§6.4, §7.1, §7.2, §12, §13; docs/schema.md)
- **Motor torque scales with mass through an editor suggestion; the format does not change (owner decision).** `motorTorqueSuggestions(doc)` in a new pure `lib/motor.js` gives each joint `roundUp2(I_eff · α + M_L · g · r_L)`, at least 0.001 N·m, where the joint graph is cut at the joint, `I_eff = I_A·I_B/(I_A+I_B)` of the two sides' inertias about the anchor (each side alone when the joint lies on a loop), `L` is the side with the smaller inertia, α = 100 rad/s², g = 10 m/s². The Hinge tool writes it into new joints; Fit motor torque (Shift+M, Edit mode, one undo step) applies it to the selected joints or to all; the new warning `W_MOTOR_OVERPOWERED` fires above 1000 × the suggestion. `motor.maxTorque` stays required and written explicitly, its schema default stays 80 (used by Add joint and when no suggestion exists), RagImporter uses the file value unchanged, and `version` stays 1, so no migration. Reason: headless liquidfun (60 Hz, 8/3) showed a 1.6 kg creature with 80 N·m everywhere gaining up to 52 J on ground contact and settling at 1 N·m, while a humanoid of 0.3–1.4 kg bodies is fine at 80 (`tests/liquidfun-motor-stability.test.js`). Cutting the graph makes the value independent of `rootBody` and bounds reaction impulses by the lighter side; the gravity term keeps tips from sagging (a 6 g tip needs ~0.002 N·m to hold itself). Rejected: α = maxSpeed/dt (1200 rad/s²), which gives that creature's hip about 125 N·m, above the failing 80; a format default for an absent field, since every field is already required (absent is `E_FIELD_MISSING`, not 80); rewriting values at load or spawn, which would silently change existing files and break the byte-identical round trip. Trade-offs: existing files keep their torques until the user runs Fit motor torque; a humanoid fitted this way gets softer distal joints (about 4 N·m at the elbow instead of 80); α, g and the 1000 factor are to be verified in the pinned build (DESIGN §12). An Inspector button is specified with #23. (DESIGN §3.1, §5.1, §5.5, §5.6, §5.7, §5.9, §6.4, §12; docs/schema.md; docs/architecture.md, Components; docs/architecture/module-map-lib-tests.md)

## 2026-10-17
- **The root transform is locked in the editor; the format does not change (#153, owner decision).** `ragdoll.position/angle` stay in format version 1 (no migration, `supportedVersions` stays `[1]`). No editor command writes them: no transform gizmo, drag or rotation for the root, read-only in the inspector; new documents write `[0, 0]` and `0`. A loaded file keeps its values as they are: they are drawn (the children are placed through them) and saved back unchanged. Spawn still ignores them and `RagDef` does not expose them; a host reads them from its JSON. New documents name the root `"root"` (schema default of `ragdoll.name` and `meta.name`); existing names, `"ragdoll"` included, are not changed. The `ragFileName` fallback for unusable names stays `ragdoll`. Reason: the owner wants the values available to runtime hosts (demo); keeping loaded values untouched keeps Load → Save byte-identical and needs no load-time normalization, and the editor's existing placement math already handles them, so only the editing paths are removed. A stored name cannot tell a default from a user choice, so renaming it would overwrite user data. Trade-offs: a file whose root was moved or rotated before this change stays that way with no editor way to reset it (edit the file); exposing the values on `RagDef` is a separate API change if a host needs it. Supersedes the same-day draft that removed the fields in a format version 2. (DESIGN §2.1, §2.2, §5.4, §5.5, §5.7, §5.8, §6.2, §7.2; docs/schema.md)

## 2026-10-16

Load → Save is byte-identical for a canonical file (latest format, no unknown fields, canonical formatting, `meta` matching the root name and the running editor); otherwise the output differs only by `meta`, migration, dropped unknown fields and formatting. No format change; `version` stays 1. Reason: `meta.editorVersion` must say which editor wrote the file to be useful for future migrations, and a second editable name would drift from `ragdoll.name`; preserving loaded values would make both fields meaningless, and a new document has no value to preserve. Trade-off: opening and saving an unchanged file in a newer editor changes one line. (DESIGN §5.3, §6.2, §6.5, §11, §12; docs/schema.md; docs/architecture/module-map.md)

Collisions are turned off in the data passed to `parse` (`filter.maskBits = 0`, `selfCollide = false` on every shape; sprites and clips stripped), not by writing `groupIndex` on spawned fixtures. Teardown: mouse joint, `rag.destroy()`, ground body, `releaseWorld` once #49 lands, world. - **Implementer choices for #44.** The mirrored `aimAxis` of each joint is kept in a private `Map` on the instance until #48 reads it. `view` is `null` after `destroy()`. `configure` accepts no `contactFilter` key until #49. `RagFormatError` names the unsupported version only when `E_VERSION_UNSUPPORTED` is the first error; otherwise it gives the error count and the first code and path. Reason: no public surface for state nothing reads yet; a destroyed instance must not hold a PIXI container. (DESIGN §7.1, §7.2)
- **Spawn contract settled for #44.** Frames: body at `S × L′`, where `L′` mirrors the root-local transform with `M(p) = (−x, y)` and negated angle under `flipX`; shapes mirror in the body frame (centers, box angle, reversed polygon vertices); anchors map as `S × M(anchor)`. Every throw (missing library, bad `world` or options, locked world) happens before any native object exists; a native failure later rolls back joints, then bodies. Joints start with the motor off; `update()` enables it. Spawn uses one scratch `b2Vec2`, destroys each def and shape after its `Create*` call, and builds polygons from a `_malloc` buffer freed right after `Set`. Reason: one mirror rule yields the existing limit `(−upper, −lower)` and `aimAxis` `π − aimAxis` rules; failing early keeps the heap and world clean; a passive ragdoll (no `update()`) is what the editor's Pose tool (#145) needs; the polygon path needs a contiguous native array, which the binding offers only through the heap (to verify, DESIGN §12). (DESIGN §7.2, §7.4, §12)
- **`parse` copies, `RagFormatError` carries the problems.** `parse` deep-copies and freezes only the fields RagImporter consumes, so later edits to the source JSON (the editor's model export) never reach a definition. `RagFormatError` exposes frozen `errors` and `warnings`; its message names the unsupported version or the first error's code and path. Reason: an immutable `RagDef` must not alias caller data; codes and paths are the stable part of a problem. (DESIGN §6.3, §7.1)
- **`configure` semantics and library resolution.** `undefined` keeps a key, `null` returns it to the global, unknown keys are ignored, and nothing is checked until `spawn`. Resolution stays private to `lib/ragimporter.js`, which passes a resolver to each `RagDef`, so no new module is needed and it remains the only reader of the globals (docs/architecture.md, Dependency rules). Reason: tests and the editor can swap and reset namespaces without import cycles. (DESIGN §7, §7.1; docs/architecture.md, Module map)
- **Host access to native objects is defined.** The host may change dynamic state (transform, velocity, damping, awake, gravity scale) and attach its own joints, which it destroys before `rag.destroy()`; it never touches fixtures, filter data, motors or limits. No damping or "pose" options are added to `spawn`. `destroy()` is idempotent, throws on a locked world, and leaves empty maps and `null` `position`/`angle`. Reason: the Pose tool needs zero gravity (host world), high damping (`SetLinearDamping`/`SetAngularDamping` after spawn), mouse joints (via `bodies`) and fast respawn, which the native handles already allow without growing the API. (DESIGN §7.1)
- **`spawn` gains a `baseUrl` option.** The default texture resolver already used `baseUrl + src` with no way to pass `baseUrl`. Reason: internal coherence of §7.1. (DESIGN §7.1, §7.3)
- **Validation details settled in #25.** `hasImage` receives the sprite asset id. A `rootBody` that points at a body whose id has an error reports `E_ROOT_BODY_UNKNOWN`. `E_JOINT_SAME_BODY` suppresses `W_ANCHOR_OUTSIDE` for that joint. `E_KEY_TIME_RANGE` is reported only for `t` above the clip length; a negative `t` is `E_FIELD_RANGE`. `W_DUPLICATE_NAME` is one warning per duplicated name within a kind, at the second occurrence, listing every colliding id; equal names across kinds do not warn. Reason: one problem per cause, no cascades. (DESIGN §6.4)
- **Validation problems are `{ severity, code, message, path, target }` with stable codes.** Every §6.4 rule has one `E_*` or `W_*` code with a fixed severity; codes are never renamed or reused. `path` is a JSON Pointer into the validated JSON, `target` is `{ type, id }` of the innermost selectable object (a clip by `key`) or `null`. Messages are English, unstable, and quote no length or angle values. An invalid input, wrong `format` or unsupported `version` stops validation after the gate; a field with an error is skipped by the rules that read it. Reason: the Problems panel (#26), load and save (#27, #28) and `parse` (#44) need machine-readable results that survive wording changes; JSON Pointer resolves duplicates and id-less objects (tracks, keys, events) by position, which ids cannot; data-unit numbers in messages would contradict the pixels-and-degrees UI. (DESIGN §6.3, §6.4, §7.1; docs/architecture.md, Validation, Module map)
- **`lib/validate.js` owns validation; `RagImporter.validate` delegates to it.** It exports `validate(json, options?)`, `SUPPORTED_VERSIONS` (also used for `RagImporter.supportedVersions`) and `PROBLEM_CODES`, and imports only `lib/schema.js` and `lib/geometry.js`. The only option is the editor's `hasImage(asset)`, which enables `W_SPRITE_IMAGE_MISSING`; the public `RagImporter.validate(json)` takes none. Reason: one implementation shared by editor and runtime, pure and testable under Node; image availability is editor state that a pure module cannot see. (DESIGN §6.4, §7.1; docs/architecture.md, Validation, Module map)
- **Schema ranges apply unconditionally: `limits.lower ≤ 0` and `limits.upper ≥ 0` hold even when limits are disabled.** §6.4 said "when limits are enabled". Not a format version bump: `lib/schema.js` already declares the bounds unconditionally, the editor's defaults and Hinge tool always satisfy them, and no `.rag.json` has been saved yet (Save is #27). Reason: one generic range check instead of a conditional hand-written one, and `flipX` and re-enabling limits never meet an inverted range. (DESIGN §6.4; docs/schema.md)
- **Unknown fields and duplicate names are validation warnings** (`W_UNKNOWN_FIELD`, `W_DUPLICATE_NAME`; bodies, shapes and joints, each kind on its own), and runtime name lookups return the first match in file order. Reason: the editor's "drop with a warning" (§6.3) needs a source, and `rag.body/joint/shape/sprite(name)` and `lookAt` resolve by name, so a repeated name silently picks one object. #25 covers the validation side of #78. (DESIGN §6.3, §6.4, §7.1)
- **Polygon validity is checked in the order count, degenerate (vertices closer than 0.0025 m or collinear within 1e-9 m²), clockwise, not convex (including stars that wind twice), with one error per polygon; anchors count as inside within 0.001 m.** Reason: one actionable error at a time; a signed-cross test alone accepts a pentagram; an anchor placed exactly on a shared edge must not warn through rounding. Thresholds to verify against the pinned build (DESIGN §12). (DESIGN §6.4, §12; docs/architecture.md, Validation)

## 2026-10-14
- **RagImporter owns one contact filter per world, and the host plugs into it.** Its `ShouldCollide` reimplements Box2D's default group/category/mask rule (bit fields `& 0xffff`), then the self-collision rule through a registry keyed by fixture pointer, then an optional host predicate set with `RagImporter.setContactFilter(world, predicate)`; a pair collides only if all three allow it. The filter is installed on the world's first `spawn` or `setContactFilter`, stays installed when the last instance goes, and is uninstalled and destroyed only by the new `RagImporter.releaseWorld(world)`, called right before the host destroys the world. Instances remove their registry entries before `DestroyBody`. The `groupIndex` fallback stays for builds without `JSContactFilter` and for hosts that opt out with `configure({ contactFilter: false })`. Reason: issue #4 spike (`tests/liquidfun-contact-filter.test.js`): a JS filter replaces the default rule, which the reimplementation matches; `userData` holds only an integer while the fixture pointer is stable and is what `ShouldCollide` receives; there is no `GetContactFilter`, so a host filter cannot be chained, only replaced; `SetContactFilter(null)` leaves no filtering at all, so uninstalling with the last instance would silently break the host's own category/mask rules; the cost is about +8 % step time for 20 humanoids. Hosts that need to collide pairs the default rule excludes cannot express that as an AND-ed predicate, hence the opt-out. Not a format change. (DESIGN §2.5, §7.1, §7.2, §7.4, §7.5, §8, §12; docs/architecture.md, Module map)
- **The liquidfun.js API surface is confirmed, and RagImporter follows fixed native-memory rules.** The pinned build exposes everything §3 and §7.2 need; motor, limit and angle methods exist only on the `b2RevoluteJoint` wrapper, so spawn casts each joint once with `Box2D.castObject` and stores it. Filter `maskBits` reads back signed and is masked with `& 0xffff`. The heap is a fixed 16 MiB that cannot grow, and exhausting it aborts the module, so: copied defs, shapes and filters are destroyed right after use; world-owned objects and getter results are never destroyed; `update()` and `sync()` allocate nothing and reuse a scratch `b2Vec2`; joints are destroyed before bodies. Reason: issue #5 spike, verified in Node by `tests/liquidfun-api.test.js`; a per-step leak would abort a running game within minutes. (DESIGN §3, §7, §7.2, §7.4, §12)
- **The pinned build supports a JS contact filter (`JSContactFilter` + `SetContactFilter`), but its integration stays open in issue #4,** and the `groupIndex` fallback stays specified until then. Reason: one filter per world, shared by instances and the host, replaces Box2D's default filtering, which the spike did not verify. (DESIGN §2.5, §12) *Superseded by "RagImporter owns one contact filter per world" above: issue #4 settled the integration and verified the default-rule replacement.*
- **RagImporter is the `lib/` folder,** with `lib/ragimporter.js` as the only public entry. Hosts copy `lib/`; `demo/` imports only the entry; the editor may import internal `lib/` modules. Reason: schema, emitter, validation, serializer and evaluator must be shared, pure and testable, which one file would not allow at a reasonable size. (DESIGN §7, §8, §9)
- **liquidfun.js is the doebi/liquidfun.js v1.1.0 Emscripten (asm.js) build**, reached through its `Box2D` namespace global with WebIDL accessors; RagImporter never assumes global `b2*` names. `RagImporter.configure` accepts `{ Box2D }` as well as `{ PIXI }`, both optional. It is the build the project owner uses, is self-contained and matches the reference demo byte for byte; injecting the namespace mirrors the PIXI handling and lets tests and module-based hosts supply it without a global. (DESIGN §7, §12)
- **PIXI.js is pinned to 8.21.0** after verifying `Assets`, `sortableChildren`/`zIndex` and `eventMode` + `pointermove`. (DESIGN §7, §12)
- **RagImporter targets LiquidFun + PIXI.js directly**, with no engine/renderer adapter layer. The project only targets this stack; an adapter layer can be added later if needed. (DESIGN §7)
- **Procedural joint control lives in RagImporter**; authoring (`aimAxis`) and preview live in the editor. Targets come from runtime data the editor cannot key. (DESIGN §4.8)
- **Shapes carry sprites** (offset, angle, scale, z), and the timeline can swap them through a discrete `sprite` channel. (DESIGN §2.3, §4.2)
- **The root is a world object** that parents everything and owns the global `strength`/`gain`/`damping` channels. These are 0–1 multipliers, never overrides, so a "dead" clip needs a single track. (DESIGN §2.1)
- **Springs are emulated with joint motors** (PD over motor speed, torque scaled by strength), because LiquidFun revolute joints have no spring. (DESIGN §3)
- **Layers:** the higher index wins; override by default, additive optional; no masks, since a clip only affects the tracks it has. (DESIGN §4.4)
- **Transitions** use per-clip `fadeIn`/`fadeOut`; a transition matrix is backlog. (DESIGN §4.1)
- **Grouping replaces FixedJoint**: a body can have several fixtures. (DESIGN §2.2)
- **The editor's Simulate mode uses RagImporter**, so preview equals production. (DESIGN §3, §5.1)
