# Decisions: Toolbar

Newest first. See the [index](../decisions.md).

## 2026-10-15
- **Select is active on load and is the toolbar's pressed button and roving stop; New and Load keep the active tool.** No code beyond registering the tool: the registry already starts with Select and `js/main.js` already refreshes the toolbar from `tools.active`. (DESIGN §5.5; docs/architecture.md, Tools)
- **Tools overlay geometry is fixed so its sizes add up:** 4 px from the outer edge to the buttons (1 px border plus 3 px padding), 2 px gaps between all items, separators 5 px tall; one column 40 × 299 px, two columns 76 × 149 px (selection + manipulation, creation + joints, 4 px apart, the middle separator hidden). The two-column threshold is derived, not a constant: the strip plus its two 8 px margins (315 px). Reason: "1 px border, 4 px padding" gave a 42 px strip, not the 40 × 299 the spec stated, and the two-column size had no arrangement behind it; deriving the threshold keeps it right if a metric changes. Viewport minimum height becomes 168 px. (DESIGN §5.2, §5.5; docs/architecture.md, Module map)
- **The overlay's testable rules live as DOM-free exports of `js/viewport/toolbar.js`** (`TOOL_BUTTONS`, `TOOLBAR_MARGIN`, `toolbarSize`, `toolbarColumns`), allowed in `tests/` by the existing UI exception, and the framing insets as `framingInsets` in the core `js/viewport/bounds.js`. `toolbar.width()` returns `toolbarSize(columns).width` instead of measuring. Reason: no new module for four small functions, and the column rule belongs next to the DOM that applies it; framing insets are a framing rule, already core. A computed width never forces layout during framing; the CSS must match it, which is checked in the browser. (DESIGN §5.4, §5.5; docs/architecture.md, Dependency rules, Module map, Viewport camera, grid and snapping)
- **`TOOL_BUTTONS` entries carry `shortcut` (the `TOOL_SPECS` hotkey) instead of `hotkey`,** so each entry is a `HeaderAction` and `actionTitle` builds the tooltip unchanged; buttons also get `aria-keyshortcuts`. Reason: one tooltip text builder for header and tools, as §5.5 requires ("built like the header tooltips"). (DESIGN §5.5; docs/architecture.md, Module map)
- **Unbuilt tools are disabled with "(not available yet)", read from the `tool:<id>` actions; at most one button is pressed, and none before Select (#13) is registered.** Confirms the #12 rule from the toolbar side: `js/main.js` refreshes every button from `actions.isEnabled`/`reason` on `tool` and `mode` events, so tools light up as their issues register them, with no toolbar change. Reason: "exactly one pressed, Select active on load" contradicted the registry rule that no tool is active without Select. (DESIGN §5.5; docs/architecture.md, Editor boot)
- **Toolbar keyboard and pointer details:** Up/Down and Left/Right both move linearly in either layout; Enter/Space use the native button click and keep focus; a pointer click on an enabled button moves focus to the viewport host, on a disabled one it does nothing; Esc only hides the tooltip and is consumed; the roving stop returns to the active tool when focus leaves; a wheel over the overlay is swallowed. Reason: handling Space in `keydown` risks a second activation from the native keyup click in some browsers; a two-dimensional grid for at most eight buttons is not worth a second navigation model; a wheel over the overlay would otherwise scroll the workspace. (DESIGN §5.5, §5.9; docs/architecture.md, Module map)
- **The tooltip is one shared, `aria-hidden`, fixed-position element on `body`, created on first show, placed 8 px right of its button; `attachTooltip` returns `{ update, detach }`.** Reason: inside the isolated Viewport panel it would be clipped and could not rise above neighbouring panels; creating it lazily keeps `js/tooltip.js`, and so `js/viewport/toolbar.js`, loadable in Node; `update` lets a visible tooltip follow a mode change. (DESIGN §5.5; docs/architecture.md, Module map)
- **No layout version change for #87.** Stored layouts that still name a `tools` panel are already rejected by `validateLayout` (version 1, or an unknown panel id) and replaced by the default with a warning, which is never an error; the raised Viewport minimum applies when rects are computed, not to stored sizes. Drag & drop loading listens on `#panel-viewport` (#28), and the overlay never stops drag events. Reason: the 2026-10-14 decision already moved the record to version 2 without migration when Tools left the dock; only tests were missing. (DESIGN §5.2, §5.3, §5.5; docs/architecture.md, Dock layout, Module map)
- **A middle press during a left tool drag stays specified as a pan, with a provisional known limitation:** if the browser takes pointer capture away on that press, the existing lost-capture rule cancels the drag and the document is left as it was. No code change in #12. Reason: the release was only observed with events injected through the Chrome DevTools Protocol, whose `buttons` mask may have dropped the left button, so it may not happen with a physical mouse; the fallback is safe (one aborted drag, no data change), zoom during a drag works, and Space + drag remains a pan path. If a real browser reproduces it, a fix (such as re-capturing while the primary button is still down) is specified then. (DESIGN §5.4, §12; docs/architecture.md, Tools)
- **The tool cursor reaches the host through the `--tool-cursor` CSS custom property,** set by `js/viewport.js` in `ToolView.setCursor` and read by `#viewport-host { cursor: var(--tool-cursor, default) }`; navigation keeps writing the inline `cursor` (`grab`/`grabbing`, else `''`), which overrides the stylesheet. Reason: DESIGN §5.5 wants the tool cursor except while navigating; using CSS precedence keeps `attachInput` unaware of tools' cursors and the registry unaware of navigation, with no shared state or signature change. (DESIGN §5.5; docs/architecture.md, Tools, Module map)
- **`createEditor` gets no `tools` option; the mode reason of a registered `tool:<id>` action is checked in the browser until #14,** whose first tool (`circleTool`) adds the Node test to `tests/editor.test.js` (refused with "not available in *Mode* mode" where `tool.circle` is not allowed). Reason: an injection option would be public API added only for one test, while the registry itself is already tested directly and the reason function is the same `modeReason` the `undo` tests cover; the gap closes with the next tool issue. (docs/architecture.md, Editor composition, Module map)
