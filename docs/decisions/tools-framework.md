# Decisions: Tool framework

Newest first. See the [index](../decisions.md).

## 2026-10-15
- **#12 UI accepted as built:** buttons pressed or released while another is held are read from `pointermove` with `button ≥ 0`; hover is throttled with `requestAnimationFrame` (not the PIXI ticker) and also cleared on window blur; `Viewport` exposes `gizmos` and `hitTest(screen)`; the gizmo layer draws nothing while the camera has no size, and a model `reset` clears hover. Reason: each follows the Pointer Events model for chorded buttons or has no visible effect beyond the spec. (DESIGN §5.4, §5.5; docs/architecture.md, Tools, Module map)
- **A tool handler that throws during a press always aborts it, `pointerUp` included:** the registry closes the press, runs `cancel()` (tool cancel, then `history.cancelGesture()`) and rethrows; nothing is recorded. This replaces "`endGesture()` also when `pointerUp` throws", which contradicted the general rule. Reason: one rule for every handler; a throw is a bug, and reverting the whole operation keeps "one operation, at most one undo step" and leaves no half-built result or stale tool state (`endGesture` would record a partial step without ever calling `tool.cancel()`). (DESIGN §1, §5.5; docs/architecture.md, Tools)
- **A cancelled press also ends at the first move without the primary button or at the next left press,** not only at its release. Right presses stay ignored until then. Reason: after a cancel caused by lost capture or blur the release may never reach the host, and the press must not block the next one. (DESIGN §5.5; docs/architecture.md, Tools)
- **#12 core details accepted as built:** `js/viewport/hit.js` imports `ROOT_UID` from `js/model/model.js` (core to core, like `placement.js`); `defineTool` ignores `label`, `hotkey`, `capability` and unknown members in a definition and throws `TypeError` for a handler, `cursor` or `hover` of the wrong type; `key()` also refuses the legacy `Esc` key value; with no active tool the cursor is `'default'`; `jointZeroAngle` treats an anchor within 1e-9 m of bodyB's origin as coinciding; `pointInShape` uses the even-odd rule, so concave and self-intersecting drafts are hit as drawn; `shapeMass` uses the absolute polygon area (a clockwise polygon weighs as its counter-clockwise twin; a concave draft counts its own area, where Box2D would hull it) and gives mass 0 for a negative or non-finite density. Reason: each keeps drafts and invalid files usable in the viewport, matches Box2D for every valid shape, or has no visible effect; type errors in a tool definition surface at load instead of at the first event. (DESIGN §5.4, §5.5; docs/architecture.md, Tools, Module map)
- **`createEditor` builds the tool registry on the #12 branch before it merges,** and its own `history.cancelGesture()` `mode` listener is removed in the same change; the transitional state, with both the registry module and the old listener, is accepted only on the branch. Reason: until then `escape`, `tool:<id>` actions and mode-change cancellation ignore tools, and two cancellation listeners must never coexist. (docs/architecture.md, Editor composition, Module map)
- **#12 gizmo and tool overlay views are stacked by `js/viewport.js` on the stage above `scene.view` (grid, scene, gizmos, tool overlay), and #12 removes the scene's empty world `gizmos` and screen-space `overlay` containers; the scene keeps no joint entries.** Both redraw from a `PIXI.Ticker.shared` callback like the grid and the scene, with no ticker parameter, and whoever calls `scene.setPose` also calls `gizmos.invalidate()`. Reason: #11 built those containers as empty placeholders from the earlier plan, while the #12 spec draws every gizmo, highlight and overlay in screen space from `js/viewport/gizmos.js`; stacking views on the stage matches how the grid is already added, keeps `Scene` unchanged, and leaves one owner per layer. The scene emits no pose event, so invalidation stays with the pose's owner. (DESIGN §5.4; docs/architecture.md, View sync, Module map)
- **Tool ids, labels, hotkeys, capabilities and toolbar groups live in one core table, `TOOL_SPECS` in `js/tools/tool.js`.** `defineTool` copies them into each tool, `HOTKEYS` builds its `tool:<id>` rows from it (first, for all eight tools, registered or not), and the Tools overlay builds `TOOL_BUTTONS` from it, adding only icons. The registry's `toolForHotkey` is dropped: tool hotkeys are ordinary `tool:<id>` actions, registered by `createEditor` for registered tools only, so unbuilt tools report "not available yet" through the existing action rule and the toolbar reads enabled state and reason from the actions like the header does. Reason: the plan had three copies (tool objects, hotkey rows, toolbar buttons) of the same ids and keys, and a static hotkey table cannot be built from tool objects that do not exist yet. (DESIGN §5.5, §5.9; docs/architecture.md, Tools, Actions and hotkeys, Module map)
- **The tool registry owns cancellation.** It is built right after `modes` and subscribes first to `mode`; `tools.cancel()` cancels the tool and any open gesture (also one it did not open), replacing the editor's `history.cancelGesture()` listener. It also watches `history`: when its press is open but the gesture was closed elsewhere (Undo, reset), it cancels the tool, so Undo during a drag needs no special case in the `undo` action. After a cancel, the rest of that press is swallowed, so a release after Esc never completes the operation. Reason: tools hold local state that a history-only cancel would leave stale. (DESIGN §1, §5.5; docs/architecture.md, Editor composition, Tools)
- **The registry completes pointer events and binds to the view late.** Input passes screen coordinates, buttons, modifiers and click count; the registry adds `world` and root-local `local` from the camera and the root transform. `hitTest`, the cursor and overlay invalidation reach tools through `bindView`, called by the viewport, and are inert until then. Tools are factories with closure state. Reason: the registry and the tools stay core and testable under Node, with no viewport and no shared state between editors. (docs/architecture.md, Tools)
- **Without a registered Select tool, no tool is active.** The registry starts on `select` when it exists and falls back to it on mode changes; Select is registered since #13, so the editor starts with it active; the no-tool fallback only remains for registries built without it. Reason: lets the creation tools (#14–#16) land before #13 without a stub Select. (DESIGN §5.5; docs/architecture.md, Tools)
- **Creation tools change the document once, on completion, then select what they created and stay active.** They preview in the tool overlay while drawing; the create command runs inside the final release's gesture. The selection gets the new shape (or joint), never its body, matching what a viewport click selects. A new shape body sits at the shape's center with the opposite of the root's angle, with the shape stored around the body origin. Reason: a model write per drag step would create invalid intermediate shapes (radius 0) and churn every view, and creating then switching to Select would break drawing several shapes in a row; the body placement gives Manipulate a natural pivot and keeps the drawn orientation when the root is rotated. Not a format change. (DESIGN §2.2, §5.5)
- **Tool input rules:** tools get left and right presses and every move; middle and Space + left stay navigation; a left drag owns the pointer (other buttons ignored); modifier changes and pans during a drag re-send the last position; lost capture or window blur cancels; Esc never reaches `tool.keyDown`. Reason: the Box modifiers and the Polygon right click need these, and a drag that silently continues after the pointer is lost leaves a gesture open. (DESIGN §5.5, §12; docs/architecture.md, Tools)
- **Hit testing is a fixed order with screen-space radii:** joints within 8 px, then the root within 12 px, then shapes containing the point or within 4 px, later objects first; bodies and sprites are never hit, invalid geometry is skipped, and the displayed pose is used. Reason: gizmos are drawn above shapes and must win; screen-space tolerances keep small shapes and points clickable at any zoom; display-mode independence was already decided. (DESIGN §5.4; docs/architecture.md, Module map)
- **Gizmos, feedback and overlays are drawn in one screen-space layer redrawn whole when dirty, at most once per frame,** with sizes and colors in a core `js/viewport/style.js` and world placement in a core `js/viewport/placement.js`. Joint arcs and needles are measured from a zero direction (anchor → bodyB origin at rest, turned with bodyA). Selection is 2 px in `#5b9cf5`, hover 1 px, invalid red wins over both. Reason: constant-size gizmos in a scaled world container would need the unverified scaled-stroke technique; a few dozen gizmos are cheap to redraw; hit testing, gizmos and the Hinge tool need the same anchor and zero-direction math; "relative to bodyA" gave no direction to draw from. (DESIGN §5.4; docs/architecture.md, View sync, Module map)
- **Overlays are editor settings (`overlay.names`, `overlay.centers`, `overlay.contacts`, default off) in a new Settings group;** the settings record stays version 1 because missing fields restore to defaults. #12 draws names and centers of mass (Box2D's mass rule); contacts are drawn by Simulate mode (#54), and the preview environment is built with #54 and #38. Invalid feedback is an input of the gizmo layer (`setInvalid`), fed once Problems (#26) runs validation. Reason: §5.3 deferred the overlay toggles to the overlays issue; contacts and the preview environment need a live world, and invalid state needs validation, neither of which exists in #12. (DESIGN §5.3, §5.4; docs/architecture.md, Module map, View sync)
- **#11 implementation details the spec left open are accepted as built:** the stored settings record nests by key prefix (`{ version, grid, snap, display }`), and a record with a missing or other `version` is ignored as a whole with one warning, like the stored layout; the camera starts at (0, 0) and 32 px/m, which matches the default `pixelsPerMeter` and is replaced by framing on start; under a pose, a joint anchor follows its `bodyA` (the parent, DESIGN §2.4) and otherwise stays at rest; `shapeBounds` throws `TypeError` for an unknown type or an empty polygon, and framing skips shapes that throw or give non-finite bounds; grid fine lines with opacity 0 are omitted, lines at world 0 are kept and the axes are drawn over them; `js/units.js` converts single numbers and throws `RangeError` when `m` has no valid `pixelsPerMeter`. Reason: each follows an existing rule (versioned stored records, FK rotates children about anchors carried by the parent, drafts and invalid files must still display) or has no visible effect, and keeping the conversion scalar leaves `vec2` handling to the inspector, which knows the field shape. (DESIGN §5.3, §5.4; docs/architecture.md, Module map)

## 2026-10-14
- **All viewport tools share one contract and a registry.** Tools implement activate/deactivate, pointer down/move/up, keyDown, cancel (Esc), cursor and screen-space overlay drawing; the registry enforces the mode policy, maps hotkeys and opens a history gesture per press–release. Navigation is handled before tools. (DESIGN §5.5; docs/architecture.md, Tools)
