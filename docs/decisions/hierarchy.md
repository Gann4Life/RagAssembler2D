# Decisions: Hierarchy and deletion

Newest first. See the [index](../decisions.md).

## 2026-10-17
- **Rename is a global F2 action on the single selected object (#153, owner feedback).** F2 is an action in the registry and `HOTKEYS`, like Delete: enabled in Edit mode with exactly one selected root, body, shape or joint, no drag or scrub, no open rename field, confirmation or menu; text fields keep their own F2. The field opens by the pointer's position at the press: inline in the object's Hierarchy row when the pointer is over the Hierarchy panel (search cleared, ancestors expanded, row scrolled into view), otherwise as a rename popup in the viewport, anchored at the pointer when it is over the viewport and at the object's on-screen point otherwise (the viewport center when that point is off-screen), kept inside the viewport. Enter or blur commits one undo step through `setProps({ name })`, an unchanged name records nothing; Esc, Undo, a mode change, New or Load cancel; empty names are allowed; focus returns to where it was. Reason: the owner wants Blender-style F2 that does not depend on tree focus; the pointer is the only signal of where the user is looking, and falling back to the object's point keeps the popup next to what is renamed when F2 comes from another panel. Double-click keeps framing. Supersedes the same-day draft (F2 on the focused tree row). (DESIGN §5.1, §5.4, §5.6, §5.9)

## 2026-10-16
- **Delete's confirmation goes through a `confirm: (request) => Promise<boolean>` option of `createEditor` (default: always `true`), backed in the browser by the new UI module `js/confirm-dialog.js` (`confirmDialog`, a native modal `<dialog>`), and the request wording is built in core.** `DeletionPlan` gains `clips` (per-clip track and key counts). `delete` stays synchronous when nothing needs confirming and is disabled while a confirmation is pending; after a `true` it re-checks its enabled rule before deleting. Reason: the core stays DOM-free and Node-tested, wording included; one option serves New (#27) too; a synchronous no-confirm path keeps every existing caller and test unchanged. (DESIGN §5.6; docs/architecture.md, Editor composition, Hierarchy and deletion, Module map)
- **The dialog's key mapping, `confirmKey`, is a DOM-free export of `js/confirm-dialog.js`, listed in the `tests/` dependency row, not a separate core module.** Enter on a focused Cancel cancels. Reason: same pattern as `js/header.js` and `js/viewport/toolbar.js`; one file instead of two for a five-case function. (docs/architecture.md, Dependency rules)
- **The confirmation states the removed objects, the track and key totals and the affected clips with per-clip counts,** extending §5.6's "clips affected and the number of tracks and keys removed". Reason: the user is deciding about the cascade, and per-clip counts show where the loss is. (DESIGN §5.6)

## 2026-10-15
- **Backspace is not a Delete key; Del is the only one.** §5.9 is unchanged. Reason: owner decision; Backspace edits text in the search field and inspector, and a second, easily hit key for a destructive action without confirmation adds risk for no gain on keyboards that have Del. (DESIGN §5.6, §5.9)
- **The Delete button's tooltip gives "the ragdoll root cannot be deleted" when only the root is selected,** an explicit exception to §5.3's rule that state-only unavailability shows no reason. The mode reason wins outside Edit mode, and a gesture shows none. Reason: a selected object that cannot be deleted is otherwise unexplained, unlike Undo with nothing to undo. (DESIGN §5.3, §5.6; docs/architecture.md, Hierarchy and deletion)
- **Hierarchy presentation from the `ui-ux-analyst` review, accepted whole:** icon-only trash Delete button right of a single Add menu button (items "Add shape", "Add joint"; focus returns to Add; a disabled Add does not open; Add clears an active search first so the new row shows); the Unlinked row as a `--warning` triangle with a muted label, toggled by double click; loop leaves with a muted "loop" badge and "→ *bodyB*" (`HierarchyItem.loopTo`, never searched); an `--error` "unassigned" badge; double click on an object row selects and frames it; ArrowDown in the search field enters the tree without selecting; external selection changes make the last revealed row the roving stop without moving DOM focus; dimmed ancestors use the muted text color, not opacity; row `aria-label`s that spell out kind, id match, loop target and unassigned state, plus a visually hidden key description on the tree. None contradicts §5.6. Reason: the review targets the cases the first draft left visual-only (marks, the group row, dimming) or ambiguous (focus after Add, entering the tree from search), and the loop target saves a trip to the inspector to find which body a loop closes to. Hovering a row to highlight its object in the viewport is out of #19 (follow-up). (DESIGN §5.6; docs/architecture.md, Hierarchy and deletion)
- **`js/tooltip.js` gains a `placement` option (`'right'` default, `'below'` for panel toolbars), `js/menu.js` names its menu from the button's `aria-label` before its text content, and `css/editor.css` adds `--error` (#e5484d) and `--warning` (#f5a524) to `:root`.** Reason: a tooltip to the right of a toolbar button at the top of a right-side panel covers its neighbour or is clamped against the window; an icon or menu button's visible text is not its name; error and warning colors will be shared by the Problems panel and the inspector, so they are tokens from the first use. Public signatures stay backward compatible. (docs/architecture.md, Module map, Hierarchy and deletion)
- **Deleting the remaining shapes of a body deletes the body, with the full body cascade (its joints, the tracks of its shapes and joints, `rootBody` reassignment).** Reason: a body without shapes is a validation error that blocks Save, has no hit area and cannot be selected in the viewport, and in the UI a shape and its body are one thing (§2.2: drawing a shape creates its body); leaving an empty body behind after Del would force a second, Hierarchy-only deletion. Confirmed by the owner on 2026-10-15. (DESIGN §2.2, §5.6; docs/architecture.md, Hierarchy and deletion)
- **Delete asks for confirmation only when it would remove animation tracks; every other deletion is immediate, and Undo is the safety net.** This narrows §5.6, which asked for a confirmation on every body deletion. Reason: in the viewport nearly every Del removes a body (the last shape of its body) and often joints, so the old rule would put a dialog in the most common edit; joints are visible and come back exactly with one Undo, while tracks are invisible in Edit mode and can span several clips. No built path can create tracks yet, so #19 computes `DeletionPlan.confirm` and tests it but ships no dialog; a follow-up builds the shared confirmation dialog (also for New, #27) before Load (#27) or tracks (#33) merge. Confirmed by the owner on 2026-10-15. (DESIGN §5.6; docs/architecture.md, Hierarchy and deletion)
- **Del deletes bodies, shapes and joints from the object selection; the root is skipped (the rest is deleted, and Delete is unavailable with only the root selected), and sprite assets and clips are left to their own panels.** With the timeline focus, Del belongs to the timeline issue (#34). Reason: the root can never be removed and blocking a whole deletion because the root is also selected would be surprising after a multi-selection; asset deletion has its own in-use rule (§5.6 Assets) and clip deletion its mode rules (§5.1, §5.8), which #19 does not build. (DESIGN §5.6; docs/architecture.md, Hierarchy and deletion)
- **`deleteObjects(uids)` computes its `DeletionPlan` inside `run`, removes tracks, joints, lone shapes and bodies with one `remove` op each, then sets `rootBody`; the plan is a separate pure function, `deletionPlan(model, uids)`.** Reason: computing in `run` means the plan can never be stale, while redo re-applies the recorded ops and never calls `run`, so ids and uids come back identical; every `remove` op carries its subtree snapshot and index, so undo is exact with no new history feature; a separate plan lets the action decide enablement and confirmation without executing anything. (DESIGN §1, §5.6; docs/architecture.md, Hierarchy and deletion)
- **Hierarchy Add runs actions (`add-shape`, `add-joint`) registered in `js/editor.js`, like `delete`;** Add shape reuses `createShapeBody` (box of the schema default size at root-local (0, 0), angle 0, label "Add shape"), and Add joint reuses `createJoint`, which now accepts `bodyA` and `bodyB` both `null` (an unassigned joint). Each selects what it created. Reason: one command per kind of creation keeps ids, names and undo identical to the tools; actions give Add and Delete the mode reason and the no-commands-in-a-gesture rule for free; `null` bodies were already allowed in the model and in drafts (schema.md). (DESIGN §5.6; docs/architecture.md, Hierarchy and deletion, Commands and undo; docs/schema.md)
- **Every body row shows its shapes, also single-shape bodies; loop joints are leaves under their `bodyA`; unlinked parts are joint trees of their own under the Unlinked group, rooted at their first body in `bodies` order, followed by unassigned joints.** Unlinked cycles are marked "loop" in the Hierarchy too, although validation only reports loops reachable from `rootBody`. Reason: two-way selection sync needs a row for every shape a viewport click can select ("grouped bodies expand" left single-shape bodies without one); the owner requires every created object, including an unassigned joint from Add, to appear; a loop joint has no child body of its own, so a leaf under its parent side is the only place that keeps the body → joint → child order; a cycle drawn without a marker would look like a joint with a missing child. (DESIGN §5.6; docs/architecture.md, Hierarchy and deletion)
- **Hierarchy selection follows the viewport's modifiers (click selects only, SHIFT toggles, CTRL removes), keyboard focus moves select (SHIFT adds, CTRL moves only), Space toggles, and there is no type-ahead.** Reason: one set of modifiers for selecting the same objects in two places; selection-follows-focus is the WAI-ARIA multi-select tree alternative that suits an editor where the inspector shows the selection; type-ahead would steal the single-letter tool hotkeys and F, and the search field covers finding by name. Range selection (file-manager SHIFT + click) is not in v1. Reviewed and accepted by `ui-ux-analyst` (CTRL + Space also toggles). (DESIGN §5.6, §5.9)
- **Hierarchy search is a case-insensitive subsequence match on name or id that keeps ancestors (dimmed) and starts expanded, with a temporary expansion state discarded when the query changes.** Reason: DESIGN said "fuzzy" without a rule; a subsequence match is the simplest fuzzy rule with predictable highlights; keeping the user's expansion state separate means a search never rearranges the tree they come back to. (DESIGN §5.6; docs/architecture.md, Hierarchy and deletion)
- **The Hierarchy splits into core `js/model/hierarchy.js` (tree items, Unlinked group, marks, fuzzy search, visible rows) and `js/tree-nav.js` (tree key moves), and UI `js/panels/hierarchy.js`; `js/model/queries.js` exports `jointEdges` and gains `referencesTo`.** Reason: panel content modules may not import from `js/panels/`, so the pure tree model cannot live next to the panel; everything that decides what is shown, focused or deleted is then tested under Node; exporting the existing edge helper keeps one edge rule for `jointTree` and the Hierarchy forest. `js/tree-nav.js` mirrors `js/roving-focus.js` and is added to the Core row. (docs/architecture.md, Dependency rules, Module map, Hierarchy and deletion)
- **Hierarchy as built (#19) differs from the spec in small ways:** the Add button shows the visible text "Add" with a chevron (still named by `aria-label`) and opens its menu on ArrowDown (first item) and ArrowUp (last item); the tree ignores Alt-modified keys; Shift+Space also toggles; the focused-row outline is drawn on `:focus-visible`; collapsing an ancestor of the roving row moves the roving stop to the collapsed row; and the dock section keeps `tabindex="0"`, so the panel is one Tab stop before the search field. The last one is open for the architect: either keep it (a landmark stop that every dock panel shares) or drop it for panels that hold focusable content. Reason: each follows from using the controls as built (text button, native key defaults, existing dock markup) and none changes what the spec decides. (DESIGN §5.6; docs/architecture.md, Hierarchy and deletion)
