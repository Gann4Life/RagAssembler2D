# Decisions: Viewport

Newest first. See the [index](../decisions.md).

## 2026-10-15
- **Name labels:** an empty name shows the object's id; the root and joint labels sit above and to the right of their gizmo, and a body label is centered just below the body origin. Reason: a centered body label covered the center-of-mass mark whenever the center sits at the origin, and a nameless object would otherwise have no label at all. (DESIGN §5.4; docs/architecture.md, Module map)
- **The Contacts overlay is a stored setting with a working checkbox that draws nothing until Simulate mode exists (#54).** Reason: DESIGN already limits contacts to Simulate mode, which is not built; disabling the checkbox would need a reason text and would be removed again by #54. (DESIGN §5.3, §5.4; docs/architecture.md, Module map)
- **A joint `anchor` that is missing or not a finite pair is not placed:** it is not framed, not hit and draws nothing; missing body and root positions stay (0, 0), as in the scene. `js/viewport/bounds.js` changes to match `js/viewport/placement.js` (it framed a missing anchor at the root origin). Reason: two rules for the same data disagreed; a gizmo at the root origin for a malformed joint would be misleading and could steal clicks from the root, while a body still needs a frame for its shapes to be drawn and reported. (DESIGN §5.4; docs/architecture.md, Module map)
- **`openSettings` returns `{ close, refresh }`, and `js/main.js` calls `refresh()` on `history`, `mode` and model `reset` events.** The popover keeps reading document data only through its adapter and subscribes to nothing but `settings`. Reason: pixels per meter changes through undo, redo and resets, and its editability through mode changes and gestures, none of which the adapter can signal; a refresh call keeps the popover free of model, history and modes imports, and a focused field is not overwritten unless it became read-only. (DESIGN §5.3; docs/architecture.md, Editor boot, Module map)
- **The grid and scene redraw from `PIXI.Ticker.shared`, and `createViewport` creates its application with `sharedTicker: true`,** instead of passing a ticker to `createGrid` and `createScene`. Reason: with the shared ticker the application's render (low priority) runs after the redraw callbacks (normal priority) in the same frame, so a change never shows one frame late, and the module signatures stay as specified. The cost is an implicit contract: those modules only work inside an application created this way. Ordering and teardown to be verified in the browser. (DESIGN §12; docs/architecture.md, View sync, Viewport camera, grid and snapping)
- **`createEditor` throws `TypeError` when `settings` is given and is not a `Settings` instance.** Reason: a plain object or a `restore` result passed by mistake would otherwise fail later at the first `get`, far from the cause. (docs/architecture.md, Editor composition)
- **A left press while Space is held counts as a drag, even without movement, so its release does not toggle Play/Pause.** Reason: the press starts a pan; toggling playback after a click the user meant as a pan would be a surprise, and "without a drag" is read as "without a pan gesture". (DESIGN §5.9)
- **`+`, `=` and `-` repeat while held.** Reason: they are viewport navigation keys handled by the viewport, not §5.9 hotkeys, and continuous zoom on a held key is what navigation keys do elsewhere; the §5.9 repeat rule is about actions that must not fire twice. (DESIGN §5.4)
- **Closing the Settings popover with its button or an outside press commits a pending valid number and reverts an invalid one; Esc reverts the field being edited, then closes.** Reason: closing moves focus away, which is a blur, so it follows the blur rule; Esc means cancel everywhere else. (DESIGN §5.3)
- **The viewport key summary is a visually hidden `<p id="viewport-keys">` inserted right after the viewport host,** not inside it. Reason: `aria-describedby` works with any element in the document, and keeping the host's only content the canvas avoids text inside the `role="application"` region. (DESIGN §5.4; docs/architecture.md, Module map)
- **Framing insets are 16 px on every side until the Tools overlay exists; its issue (#87) adds the overlay width on the left.** Reason: DESIGN §5.4 defines the left inset as overlay width plus 16 px, and the width is 0 while there is no overlay. (DESIGN §5.4; docs/architecture.md, Viewport camera, grid and snapping)
- **Sprites display mode hides the whole shapes layer for now; hover and selection outlines will be drawn in the gizmos layer (#12), and sprites appear with the asset store (#21).** Until then the viewport shows only the grid in Sprites mode. Reason: DESIGN §5.4 keeps only hover and selection outlines in that mode, and those belong with the other highlights; hiding one layer is simpler than styling every shape as invisible. (DESIGN §5.4; docs/architecture.md, View sync)
- **Grid colors:** lines white at alpha 0.07 times the fine-level ramp (fine) and 0.16 (coarse); X axis `#e0524f` and Y axis `#58b85c` at alpha 0.9 (about rgb(204, 77, 74) and rgb(82, 169, 86) over the `#1b1d21` background), drawn over the lines. Reason: DESIGN fixes only red and green axes; the values are the implementer's choice, kept faint so shapes stay readable, and live as constants in `js/viewport/grid.js`. (DESIGN §5.4; docs/architecture.md, Module map)
- **The viewport camera stores `scale` in CSS px per meter, independent of `pixelsPerMeter`,** clamped to 2–10 000 px/m, with `center` clamped to ±10 000 m. Changing `pixelsPerMeter` keeps shapes in place on screen and resizes the sprites; resizing the viewport keeps `center` and `scale`. The camera is session state, framed to everything on start, New, Load and recovery. Reason: a zoom factor relative to `pixelsPerMeter` would make the limits, the grid density and the float range depend on file data, and showing sprites change size is exactly what the setting does. (DESIGN §5.4; docs/architecture.md, Viewport camera, grid and snapping)
- **Wheel zoom is `2^(−Δy / 400)` (`2^(−Δy / 100)` for Ctrl, i.e. trackpad pinch) around the pointer, and `+`/`-` zoom by √2 around the center;** there is no keyboard pan. Reason: DESIGN gave no rate or keyboard zoom; F and Home already bring any content into view without a pointer, and arrow keys stay free for tools. Rates are provisional until checked in browsers (DESIGN §12). (DESIGN §5.4, §12)
- **Framing fits the bounds of shapes, joint anchors and the root position, grown to at least 1 m (4 m for an empty ragdoll), without sprite images,** with insets of 16 px plus the Tools overlay width on the left. Reason: sprite sizes need textures, which live outside the core and the model; shapes are what users place sprites on, and a point-sized selection (a joint) needs a finite box. (DESIGN §5.4; docs/architecture.md, Module map)
- **The grid has a configurable size and subdivisions (defaults 1 m and 10) and draws at most two adaptive levels,** the finest at least 8 px apart (fading in up to 32 px) and the next coarser one; levels above the major spacing step by 10. Reason: §5.3 listed "grid size" in Settings while §5.4 fixed 1 m / 0.1 m; fixed levels become a solid fill when zoomed out. (DESIGN §5.3, §5.4)
- **Grid snap rounds to the minor spacing in world coordinates, whatever level is displayed and whether the grid is shown;** it applies to points that tools place or drag, circle radii round to the step, and sprite edit, Pose, inspector fields and Hierarchy additions never snap. SHIFT angle snap stays fixed at 15° and applies to the edited angle in its own frame. Reason: a snap step that changed with zoom would be unpredictable; snapping in world space matches the grid the user sees. When the root is moved or rotated off the grid, root-local values are not on round numbers, which is accepted. (DESIGN §5.4)
- **Display modes are a table:** Shapes (filled at 40 %, sprites hidden), Sprites (shapes hidden except hover and selection outlines), Both (60 % outlines over sprites); hit testing ignores the mode. Reason: "translucent outlines" did not say what Shapes and Sprites modes draw, nor whether hidden shapes can be selected. (DESIGN §5.4)
- **Settings is a non-modal popover from the header button; editor settings are saved per browser under `ragassembler.settings`,** restored field by field (invalid fields fall back to defaults with a warning), never undoable. Pixels per meter appears there too but stays a document edit with one undo step per commit, Edit mode only. Reason: DESIGN listed the settings but not their control, persistence or undo status; a per-field restore keeps valid settings when one field is bad, unlike the layout, whose parts depend on each other. (DESIGN §5.3; docs/architecture.md, Module map)
- **The viewport host becomes `role="application"` with #11,** whose navigation keys (Space, `+`, `-`) are its first own keys, as the 2026-10-14 decision foresaw. (DESIGN §5.4)
- **Viewport logic is split into core modules tested under Node:** `js/viewport/camera.js`, `js/viewport/bounds.js`, `js/viewport/grid-lines.js`, `js/viewport/snap.js` and `js/settings.js`; `js/viewport/grid.js`, `input.js`, `scene.js`, `js/settings-dialog.js` and the storage functions only route events and draw. #11 creates `lib/geometry.js` (`transformPoint`, `composeTransforms`, `shapeBounds`) and `js/units.js`, as their first consumer. `Camera` and `Settings` are owned by `createEditor()`, which takes the restored `Settings` as an option (`createEditor({ settings })`, defaults when omitted) because the core reads no storage. `settings`, `frame-selection` and `frame-all` are registered by `js/main.js`, like the other actions that need the DOM, and Space taps reach `toggle-play` through the action registry. Reason: the numeric rules are where bugs hide and must not need a browser to test; the layers table drives the conformance checks. (docs/architecture.md, Dependency rules, Module map, Editor composition, Viewport camera, grid and snapping)

## 2026-10-14
- **The viewport host stays `role="group"` until the viewport handles keys itself, then becomes `role="application"`.** Reason: screen readers use single-key hotkeys (V, B, M, F, Space…) for browse-mode navigation unless the focused region is an application, and an application role is not justified before there are keys to pass through. Its scope is limited to the viewport host. (DESIGN §5.4)
