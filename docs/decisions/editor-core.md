# Decisions: Editor core

Newest first. See the [index](../decisions.md).

## 2026-10-16
- **Group, Ungroup and Split are core actions `group`, `ungroup` and `split` (#18), gated like `delete` (Edit mode, no gesture, no pending confirmation, shared `confirming` flag), each selecting the shapes its command returns; `group` asks through `confirm` with a new `'group'` request only when internal joints would be deleted, and re-checks its rule after the answer.** They give state reasons ("select shapes of two or more bodies", "each selected body has a single shape", "select some, not all, shapes of a body", "a shape has invalid geometry"), another exception to §5.3's no-reason rule, like Delete's root reason. Reason: same pattern and tests as Delete; a joint deletion inside Group is less expected than Del's, so it always warns, not only when tracks go; the reasons are what the owner asked for a single-shape body and cost nothing until a menu shows them. (DESIGN §2.2, §5.9; docs/architecture/grouping.md, Editor composition, Actions and hotkeys)
- **Split is bound to Alt+G, and an Alt + letter row also matches by `event.code` when `event.key` is not an ASCII letter.** Reason: Option on macOS turns G into "©", so the character rule of §5.9 alone would make Alt+G dead on Macs; limiting the fallback to non-letter keys keeps character matching on Windows and Linux Latin layouts, where Alt leaves the letter alone, and AltGr (Ctrl+Alt) still never matches. Alt+G has no default browser binding in Chromium or Firefox; browser behavior is listed in §12 to verify. (DESIGN §5.9, §12; docs/architecture/actions-and-hotkeys.md)
- **Load and Save are core actions with injected I/O (#28).** `createEditor` gains `files: { openText(), saveText(fileName, text) → Promise<boolean> } | null` and `notify(notice)`; `load`/`save` are registered only when `files` is given. Both picker and drop go through `Editor.loadFrom(read)`, which calls `read` synchronously (the picker needs the user activation), then confirms with a `'load'` request when dirty, then `loadJson`; file first, confirmation after. Save is `saveJson` (new in `js/model/io.js`: `toJson` → `validate` → `serialize` + `ragFileName`), then `await files.saveText`, then the existing `history.markSaved()` only when it resolved `true`; where the browser has a save-file picker the user chooses the name and place and cancelling keeps the document dirty, otherwise it counts as saved once the download starts. A pending save disables New, Load and Save. Errors and load notes go to a message variant of the shared dialog (`noticeDialog`, one OK button) until the Problems panel (#26) exists. `js/files.js` only reads, downloads and wires drops (input file, Blob link, the save picker of the File System Access API when present, a download otherwise). New, Load and Save share `canFile` (mode `file`), so New is now also available in Animate as §5.1 says. Reason: keeps every rule (confirmation, rejection, notes, clean state, wording) testable under Node with fakes, reuses the confirmation pattern of #124, and keeps the UI layer to thin browser adapters. Trade-off: an invalid file is only rejected after the discard confirmation (the document is still unchanged); splitting `loadJson` into check and commit was not worth it now. (DESIGN §5.3, §5.1; docs/architecture/editor-composition.md, model-io.md, editor-boot.md, module-map.md)
- **The editor version reaches `toJson` through `createEditor({ editorVersion })` (#27).** `js/version.js` (core, `fetch` injected) exports `loadVersion(fetchFn) → Promise<{ editorVersion, label }>`, never rejecting and falling back to `dev`; `js/main.js` calls it once, updates the label and a variable read by the getter `editorVersion: () => string` it passes to `createEditor`. The editor exposes `Editor.editorVersion` and the registry `ToolContext.editorVersion`, so Pose, Problems and Save all use the same value; the Pose session's `'0.0.0'` placeholder is removed. Not a physics-service option: the version is document export data, not physics, and Problems and Save have no physics service. A getter, not a string, because `version.json` arrives after boot and Save during the fetch must write `dev` (DESIGN §6.5). (DESIGN §6.5; docs/architecture/model-io.md, Editor composition, Module map)

## 2026-10-15
- **`ActionRegistry.isRepeatable(id)` is part of the registry API,** read by `dispatchKey` for key repeat. Reason: the spec gave `ActionSpec.repeatable` but no way for the dispatcher to read it without reaching into the stored specs. (docs/architecture.md, Actions and hotkeys)
- **DOM actions stay registered in `js/main.js`.** #10 moved the Window menu, panel toggles and Reset layout behind `actions.run`, but their registration needs the dock and header, so it lives in `js/main.js`; `js/editor.js` registers only DOM-free actions. The menu's Down/Up opening stays on the button. Reason: `js/editor.js` is core and cannot touch the DOM. (docs/architecture.md, Editor boot, Actions and hotkeys)
- **New, with its unsaved-changes confirmation, is built with #27,** not #10. `history.dirty` is ready for it. Reason: New needs `newDocument` and the `reset` path of `js/model/io.js`, which #27 creates; an action whose feature is not built stays unregistered and reports "not available yet". (DESIGN §5.3; docs/architecture.md, Module map)
- **The editor subscribes its cancellation listener to `modes` before anything else.** Reason: emitters run in subscription order, so Simulate start (#54) and other `mode` listeners never observe a half-done gesture. (DESIGN §5.1; docs/architecture.md, Editor composition)
- **The playhead resets to 0 when another clip is opened and is clamped to the clip length; a removed open clip or a reset returns to Edit mode.** Reason: DESIGN did not say what happens to the open clip when undo or delete removes it, or where the playhead goes between clips. (DESIGN §5.1; docs/architecture.md, Modes)
- **Hotkeys match `event.key` with exact modifiers, Cmd counts as Ctrl, a match always calls `preventDefault`, and only Undo, Redo and Next frame repeat.** Reason: `key` follows the user's layout, which is what the printed shortcut means; a disabled Save must still not open the browser's save dialog; repeating toggles (Space, tools, Delete) on a held key is never intended. (DESIGN §5.9; docs/architecture.md, Actions and hotkeys)
- **Disabled header actions state why:** "(not available yet)" when not built (not registered), "(not available in *Mode* mode)" when the mode policy refuses, nothing when only state disables them. `ActionRegistry` gains `has` and `reason`, and `actionTitle`/`setActionEnabled` take the reason. Reason: once Undo and Redo are built, "(not available yet)" on an empty stack would be false. (DESIGN §5.3; docs/architecture.md, Actions and hotkeys, Module map)
- **#10 builds modes as core state only.** Play, Pause, Next frame and Stop stay unregistered (disabled, "not available yet") until #54, and Edit/Animate switching gets its UI with the Timeline (#32). Reason: entering Simulate without a simulation, or Animate without a timeline, would show nothing; the state and policy are tested in Node now so later issues only wire them. (DESIGN §5.1, §5.3; docs/architecture.md, Modes, Editor composition)

## 2026-10-14
- **Mode policy is a table in DESIGN §5.1** and a `MODE_POLICY` capability map in `js/modes.js`. Animate edits only the open clip (plus asset import), so rest-pose fields are read-only there and Manipulate only rotates; Simulate is read-only except selection, preview and playback. Changing mode cancels the current tool operation. Reason: DESIGN said "Edits affect: keys of the open clip" without saying which controls that disables. (DESIGN §5.1)
- **Hotkeys go through one dispatcher** with a fixed order (text fields and handled events ignored, then the focused viewport's tool, then the global table), and Space toggles Play/Pause on release only if no Space + drag pan happened; on a focused button Space keeps its native meaning. Reason: Space is both a pan modifier and the Play/Pause hotkey. (DESIGN §5.9; docs/architecture.md, Actions and hotkeys)
